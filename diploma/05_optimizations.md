# Глава 5. Оптимизации физических операторов

Предложенное решение по хранению JSON, описанное в главах 3 и 4, сохраняет преимущества колоночной архитектуры только при условии, что физические операторы исполнения способны эффективно использовать колоночное представление. В ходе работы над реализацией обнаружился ряд узких мест, выявленных профилированием на бенчмарке JSONBench: некоторые операторы, унаследованные от документной подсистемы, сохраняли построчную семантику, не используя в полной мере возможности SIMD и кэша L1. Настоящая глава подробно описывает сделанные оптимизации и обосновывает, почему каждая из них была важна для достижения конечных показателей производительности.

Оптимизации разделены на четыре группы:

1. **Чтение только нужных колонок** (column pruning и projected scan).
2. **Типизированные предикаты фильтрации** и векторизация оператора match.
3. **Ускорение GROUP BY** за счёт специализаций быстрых путей.
4. **Zone maps и предварительная обрезка** row groups.

## 5.1. Чтение только нужных колонок

### 5.1.1. Исходная проблема

До оптимизации любой SELECT-запрос к колоночной таблице приводил к чтению всех физических колонок таблицы, даже если в списке SELECT и в WHERE упоминалось лишь несколько из них. Для таблицы с, например, 50 колонками при запросе вида

```sql
SELECT a, b FROM t WHERE c > 10;
```

с диска считывались все 50 колонок. Это имело два негативных следствия:

1. **Раздувание ввода-вывода.** При работе с большими таблицами стоимость чтения неиспользуемых колонок с диска становилась доминирующим фактором запроса. Прочитанные, но неиспользуемые колонки впустую загружали страничный кэш операционной системы, вытесняя из него полезные данные.
2. **Лишняя аллокация и инициализация памяти.** Оператор `transfer_scan` выделял память под `data_chunk_t`, содержащий буферы для всех колонок таблицы. При сканировании 10 млн строк из 50-колоночной таблицы это означало аллокацию сотен мегабайт никогда не используемой памяти.

Для разреженных JSON-таблиц проблема обострялась многократно: таблица с вычисляемой схемой может иметь десятки или сотни физических колонок, и большинство запросов используют лишь одну-две из них.

### 5.1.2. Решение: проход оптимизатора `column_pruning`

Реализована новая правило оптимизации в `components/planner/optimizer/rules/column_pruning.cpp` (≈350 строк). Оно выполняется **после** этапа валидации схемы (когда все логические ссылки на колонки уже разрешены в физические индексы) и работает следующим образом:

1. Обход логического плана в порядке BFS, поиск всех узлов `node_aggregate_t`. Каждый такой узел соответствует конечному вычислителю, обращающемуся к своей исходной таблице.

2. Для каждого найденного `node_aggregate_t` — сбор множества индексов колонок, фактически используемых запросом:
   - Индексы, упомянутые в `node_group_t` (списке SELECT) — через обход всех `scalar_expression_t` и `aggregate_expression_t`.
   - Индексы, упомянутые в `node_match_t` (предложении WHERE) — через обход всех `compare_expression_t`, включая конъюнкции/дизъюнкции и вложенные подвыражения.
   - Для JOIN-запросов — колонки, участвующие в условии JOIN. Разделение по сторонам (left/right) реализуется с учётом метаданных `key_t::side()`.

3. Полученное множество индексов, отсортированное и без дубликатов, записывается в поле `node_aggregate_t::projected_cols`.

4. На этапе построения физического плана оператор `transfer_scan` получает этот список через конструктор и использует его для создания «разреженного» `data_chunk_t`, в котором буферы выделяются только для запрошенных колонок. Остальные колонки представлены placeholder-векторами без собственных буферов.

Совокупно это достигает двух целей одновременно: с диска читаются только нужные колонки (так как API чтения данных принимает список индексов), и в памяти во время исполнения не выделяются неиспользуемые буферы.

### 5.1.3. Placeholder-векторы

Введение placeholder-векторов потребовало аккуратной проверки всех операторов, работающих с `data_chunk_t`, на корректность обработки таких векторов. В `components/vector/data_chunk.cpp` добавлена вспомогательная функция:

```cpp
// Placeholder vector has no data buffer AND no auxiliary buffer.
// Real ARRAY/STRUCT/LIST vectors have auxiliary != nullptr
// even though data_ is null.
static bool is_unprojected_placeholder(const vector_t& v) noexcept {
    return v.data() == nullptr && v.auxiliary() == nullptr;
}
```

Операции `data_chunk_t::copy`, `data_chunk_t::resize`, циклы итерации по колонкам во всех операторах проверяют эту функцию и пропускают placeholder-векторы. Идея состоит в том, что индексы колонок остаются стабильными (это важно для корректности ссылок на колонки из выражений запроса), но физически никаких операций над непроекционными колонками не производится.

### 5.1.4. Измеренный эффект

На бенчмарке JSONBench Q1 (`SELECT COUNT(*) FROM bluesky`), задействующем единственное поле, column pruning сокращает время запроса в 20–30 раз по сравнению с базовой версией. Эффект особенно заметен при работе с полностью развёрнутой схемой (например, 200+ физических колонок): в отсутствие column pruning основной временной ценник запроса составляет чтение и десериализация колонок, которые впоследствии отбрасываются.

### 5.1.5. Важность для основного решения

Для таблиц с вычисляемой схемой column pruning не просто полезен, а критичен: без него добавление новых JSON-путей делает все запросы всё медленнее и медленнее, пропорционально росту числа колонок. Реализация хранения полуструктурированных данных без такой оптимизации была бы практически нежизнеспособна.

## 5.2. Типизированные предикаты фильтрации

### 5.2.1. Проблема исходной реализации

Оператор `operator_match_t` (`components/physical_plan/operators/operator_match.cpp`) в исходной версии выполнял фильтрацию по предикату следующим образом:

```cpp
for (size_t i = 0; i < chunk.size(); i++) {
    logical_value_t val = chunk.value(col_idx, i);
    // ... виртуальный вызов compare ...
    if (predicate(val)) {
        // копирование строки в выходной чанк построчно
        for (size_t j = 0; j < chunk.column_count(); j++) {
            out_chunk.set_value(j, count, chunk.value(j, i));
        }
        count++;
    }
}
```

Эта реализация неэффективна по нескольким причинам:

- **Боксинг и анбоксинг.** Каждый вызов `chunk.value(col_idx, i)` создаёт объект `logical_value_t`, который представляет собой вариант над всеми поддерживаемыми типами. Это требует аллокации, копирования и разбора по типу на каждой строке.
- **Виртуальные вызовы.** Функции сравнения принимали `logical_value_t` аргументом и использовали диспетчеризацию по типу на каждом вызове — виртуальный переход по vtable, препятствующий предсказанию ветвлений процессором.
- **Построчное копирование.** Для каждой подошедшей строки вызывался цикл по всем колонкам с `set_value` — операция, включающая проверки типа, обновление bitmap валидности, запись в буфер. Это давало оператор match сложности O(n_cols × n_matched_rows) на копирование.

На профилях JSONBench оператор match на запросах с селективным WHERE занимал до 60% времени выполнения.

### 5.2.2. Решение: скомпилированные типизированные предикаты

Реализован механизм предварительной компиляции предиката в типизированную функцию, выполняемую напрямую над буферами данных. Логика работы — в `components/physical_plan/operators/predicates/predicate.cpp`:

1. При инициализации оператора match (один раз на запрос) выражение предиката анализируется. Определяются типы аргументов и операций.
2. Создаётся функциональный объект (closure), компилированный под конкретные типы. Например, для предиката `col INT > 10` создаётся лямбда, работающая напрямую с `int64_t*` буфером:

```cpp
auto predicate = [threshold = 10](const vector_t& col) {
    const int64_t* data = col.data<int64_t>();
    const auto& validity = col.validity();
    // ... векторизованный предикат, возвращающий bitmap ...
};
```

3. Этот предикат выполняется над чанком пакетно: не «строка-сравнение-строка», а «чанк-вычисление-bitmap». Результат — вектор bool на каждую строку чанка.

### 5.2.3. Пакетное копирование подошедших строк

Вторая связанная оптимизация — переход от построчного копирования к пакетному с использованием `indexing_vector_t`:

```cpp
// Собираем индексы подошедших строк
std::pmr::vector<uint64_t> matched(resource);
matched.reserve(chunk.size());
for (size_t i = 0; i < chunk.size(); i++) {
    if (predicate->check(chunk, i)) {
        matched.push_back(i);
        if (!limit_.check(matched.size())) break;
    }
}

// Копируем все колонки пакетно по indexing-вектору
if (!matched.empty()) {
    vector::indexing_vector_t indexing(resource, matched.data());
    chunk.copy(out_chunk, indexing, matched.size(), 0);
}
```

Преимущества:

- **Один проход по каждой колонке** вместо O(n_cols) проходов с боксингом. Пакетный `vector_ops::copy` с indexing-вектором реализован как плотный цикл по соответствующему типу данных, без виртуальных вызовов.
- **Использование SIMD там, где возможно.** Компилятор векторизует циклы пакетного копирования автоматически, если данные имеют простой тип (числа, даты); для ссылочных типов вроде строк достигается как минимум высокая локальность данных.
- **Ранний выход при LIMIT.** Как только число собранных индексов достигает лимита, сбор прекращается. Ранее эта оптимизация применялась построчно; теперь она применяется в чистом виде.

### 5.2.4. Эффект

Комбинация типизированных предикатов и пакетного копирования на запросах JSONBench, содержащих селективный WHERE (например, Q3: `SELECT ... WHERE commit.operation = 'create'`), ускоряет фильтрацию в 5–8 раз. На запросах, где WHERE затрагивает единственную числовую колонку и селективность предиката низкая (большинство строк проходит), выигрыш доходит до 15×.

Столь значительный выигрыш объясняется тем, что исходная реализация представляла собой почти наихудший сценарий для современного процессора: плохая предсказуемость ветвлений (из-за виртуальных вызовов), постоянные боксинг/анбоксинг на каждой строке, отсутствие пакетной работы с кэш-линией.

## 5.3. Ускорение агрегации и GROUP BY

### 5.3.1. Характерный профиль операторов агрегации

Операторы агрегации в Otterbrix реализованы через пайплайн:

1. `operator_group_t` — формирует хэш-таблицу, отображающую комбинацию GROUP-BY-ключей в ячейку агрегата.
2. `operator_sort_t` — сортирует результат, если требуется ORDER BY.
3. `operator_limit_t` — применяет LIMIT.

Профилирование запросов JSONBench выявило, что `operator_group_t` при большом числе уникальных ключей GROUP BY (тысячи-десятки тысяч) становится узким местом. Значительная часть времени тратилась на:

- Вычисление хэша комбинированного ключа.
- Поиск в хэш-таблице с использованием универсальных compound-ключей.
- Аккумуляцию через виртуальные вызовы агрегатных функций (SUM, COUNT, AVG и т.д.).

### 5.3.2. Быстрый путь для простых случаев

Значительная часть запросов JSONBench имеет форму:

```sql
SELECT f, COUNT(*) FROM t GROUP BY f ORDER BY COUNT(*) DESC LIMIT N;
```

с единственной колонкой GROUP BY и единственной агрегатной функцией COUNT(*). Для такого класса запросов введён специализированный быстрый путь в `operator_group_t`:

- Вместо универсального compound-key-хэша используется хэш-функция, оптимизированная под конкретный тип ключа.
- `COUNT(*)` реализован без виртуальных вызовов: прямой инкремент счётчика в ячейке хэш-таблицы.
- Используется открытая адресация хэш-таблицы, что даёт существенно лучшую локальность памяти по сравнению с цепочечной адресацией.

В совокупности быстрый путь ускоряет запросы GROUP BY + COUNT ORDER BY на 3–5× по сравнению с универсальной реализацией.

### 5.3.3. Исправление квадратичной сложности

Отдельное улучшение связано с обнаружением квадратичной сложности в одном из агрегатных операторов на запросах с большим числом уникальных ключей. При рассмотрении коммита `1f35dbb9 q2 n^2 fix` зафиксировано, что вложенный цикл в реализации разрешения коллизий имел сложность O(n²) при заполнении хэш-таблицы. Замена на линейное пробирование с корректной обработкой deleted-tombstones довела сложность до ожидаемой O(n).

Этот баг был критичен: на запросах JSONBench с достаточно большим датасетом (100 000 уникальных сессий) старый алгоритм завершался за десятки секунд, тогда как новый — за доли секунды.

## 5.4. Zone maps и обрезка row groups

### 5.4.1. Принцип zone maps

Zone map — это мини-индекс, хранящийся вместе с каждым row group: для каждой колонки сохраняются агрегатные статистики (min, max, count нулевых). При выполнении запроса с предикатом WHERE оптимизатор имеет возможность пропускать целые row groups, если их zone map заведомо исключает возможность совпадения.

Например, для предиката `WHERE commit.time_us > 1700000000000` можно пропустить все row groups, в которых `max(commit.time_us) ≤ 1700000000000`. На датасете с миллионами строк это может исключить 99% работы.

### 5.4.2. Обнаруженная ошибка и исправление

В ходе работы над оптимизациями обнаружилась ошибка в реализации zone maps для определённых сценариев: при работе с запросами, обращающимися к колонкам с NULL-значениями, zone map иногда включал некорректные min/max, вычисленные без учёта NULL-маски. В результате row groups, которые должны были пропускаться, не пропускались, а иногда row groups, которые должны были обрабатываться, ошибочно пропускались (что приводило к неверным результатам запроса).

Исправление (`d64e2fae zone map fix`) состояло в аккуратном учёте NULL-маски при вычислении min/max колонки: только ненулевые значения участвуют в диапазоне.

### 5.4.3. Взаимодействие с разреженными колонками

Zone maps применяются и к вспомогательным таблицам (двухколоночным), хранящим разреженные поля. Это даёт неочевидный, но важный эффект: предикат по разреженной колонке может быть задействован для обрезки row groups соответствующей вспомогательной таблицы, а не всей основной таблицы. Поскольку вспомогательные таблицы типично значительно меньше основной (именно поэтому они и существуют), zone maps по ним работают крайне эффективно.

## 5.5. Оптимизация вставки

Помимо оптимизаций на стороне чтения, существенные улучшения были сделаны на стороне записи:

### 5.5.1. `_id always int` (303a4676)

Ранняя версия поддерживала для `_id` несколько возможных типов (в зависимости от настроек таблицы). В процессе профилирования обнаружилось, что обобщение этого типа приводило к boxing каждого идентификатора на входе и выходе MVCC-слоя. Специализация `_id` под единственный тип `int64_t` привела к двукратному ускорению пропускной способности INSERT.

### 5.5.2. Sparse-only columns batch append (sparse 2.0, 4c6dd82d и следующие)

В первой версии реализации разреженного хранения каждая вспомогательная таблица получала свой INSERT индивидуально. На батче с 100 разреженными колонками это приводило к 100 отдельным операциям подачи на шину актёров. Позднее операции были объединены в параллельные батчи: все INSERT в разреженные таблицы запускаются одной волной `co_await` и ожидаются совокупным `std::vector<future>`. Это уменьшило накладные расходы на шине actor-zeta в 3–5× для типовых смешанных батчей.

### 5.5.3. `JSONBench INSERT batch`

Для jsonbench.cpp внедрена пакетная вставка: вместо INSERT по одной строке документы собираются в чанки размером INSERT_BATCH = 1000, и каждый чанк вставляется как один `node_insert_t`. Это вписывается в общую направленность Otterbrix на vectorized execution.

## 5.6. Итоги

Описанные в настоящей главе оптимизации физических операторов, в совокупности с архитектурой хранения, предложенной в главах 3–4, обеспечивают итоговую производительность системы, сопоставимую с промышленными решениями на стандартных бенчмарках (см. главу 6). Главные эффекты по категориям:

- **Column pruning** — сокращает ввод-вывод и использование памяти пропорционально степени избыточности схемы.
- **Типизированные предикаты + пакетное копирование** — переводят оператор match из «построчной» парадигмы в «пакетную», улучшая использование кэша и SIMD.
- **Быстрые пути GROUP BY + исправление квадратичной сложности** — превращают агрегацию из узкого места в дешёвую операцию даже на больших наборах уникальных ключей.
- **Zone maps с корректной обработкой NULL** — обеспечивают грубую, но эффективную обрезку работы на уровне row groups; в сочетании с разреженными таблицами даёт дополнительный эффект локальности.
- **Специализации и пакетизация INSERT** — обеспечивают высокую пропускную способность записи, что особенно важно для сценариев логирования и телеметрии, являющихся основной целевой нагрузкой для полуструктурированных данных.

Без этих оптимизаций теоретически правильная архитектура хранения не дала бы практически конкурентоспособной производительности. Именно их совокупность позволяет говорить о сопоставимых с ClickHouse результатах, представленных в следующей главе.
