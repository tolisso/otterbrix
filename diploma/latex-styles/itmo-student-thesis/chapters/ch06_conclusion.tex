\chapter{Сравнительное тестирование}\label{ch:results}

\section{Методика тестирования}

Для оценки качества реализованного решения использован стандартный
бенчмарк JSONBench~--- набор аналитических запросов над потоком
JSON-событий из публичного потока сети
Bluesky~\cite{jsonbench}. Бенчмарк содержит около 40~млн событий; в
рамках тестирования использовался срез из 500~000 строк, достаточный
для получения репрезентативных показателей.

Сравниваемые системы:
\begin{itemize}
    \item \textbf{Otterbrix} (предложенное решение)~--- сборка
    основной ветки разработки, включающая все оптимизации из
    главы~5. Использован режим разреженных колонок с
    \texttt{sparse\_threshold~=~50\,000} (10\% от объёма данных) и
    закреплёнными полями \texttt{kind},
    \texttt{commit.operation}, \texttt{commit.collection},
    \texttt{did}, \texttt{time\_us}.
    \item \textbf{ClickHouse~24.10} с новым типом \texttt{JSON},
    те же пять полей объявлены как закреплённые.
    \item \textbf{PostgreSQL~17} с типом JSONB и функциональными
    индексами на пяти ключевых полях.
\end{itemize}

Измерения выполнялись на машине с процессором AMD Ryzen~7~5800X
(8~ядер, 16~потоков, 3.8~ГГц), 32~ГБ DDR4, NVMe SSD, под
управлением Ubuntu~24.04 LTS. Все кэши предварительно прогревались
однократным прогоном; фиксировалось среднее время из 5 повторных
прогонов.

\section{Набор запросов}

Использовался стандартный набор из пяти запросов:
\begin{itemize}
    \item \textbf{Q1.} \texttt{SELECT COUNT(*) FROM bluesky}~---
    базовое сканирование.
    \item \textbf{Q2.} \texttt{SELECT kind, COUNT(*) FROM bluesky
    GROUP BY kind}~--- агрегация по закреплённому полю.
    \item \textbf{Q3.} \texttt{SELECT commit.collection, COUNT(*)
    FROM bluesky WHERE commit.operation = 'create' GROUP BY
    commit.collection ORDER BY 2 DESC LIMIT 10}~--- агрегация с
    фильтром.
    \item \textbf{Q4.} \texttt{SELECT commit.record.langs,
    COUNT(*) FROM bluesky GROUP BY commit.record.langs ORDER BY 2
    DESC LIMIT 10}~--- агрегация по разреженному пути.
    \item \textbf{Q5.} \texttt{SELECT did, COUNT(*) FROM bluesky
    WHERE commit.record.reply IS NOT NULL GROUP BY did ORDER BY 2
    DESC LIMIT 10}~--- комбинация фильтра по разреженной колонке и
    агрегации по закреплённой.
\end{itemize}

Q1--Q3 задействуют преимущественно закреплённые поля, что тестирует
путь основной колоночной таблицы. Q4 и Q5 требуют обращения к
разреженным колонкам~--- тест правильности LEFT~JOIN-реконструкции
и её производительности.

\section{Интерпретация результатов}

\subsection{Запросы по закреплённым полям}

На запросах, задействующих исключительно закреплённые колонки
(Q1--Q3), Otterbrix демонстрирует показатели, сопоставимые с
ClickHouse. Разрыв составляет 20--30\%, что объясняется более
зрелой реализацией ClickHouse: десятки лет оптимизации, собственные
ассемблерные ядра SIMD, глубокая интеграция между слоями.

В то же время отрыв от PostgreSQL составляет от 10$\times$ до
20$\times$, что подтверждает фундаментальное преимущество
колоночного хранения над JSONB даже при наличии функциональных
индексов.

\subsection{Запросы по разреженным полям}

Наиболее интересными являются запросы к разреженным полям~---
именно они тестируют принципиально новую часть архитектуры.

На Q4 (чистая агрегация по разреженной колонке) Otterbrix медленнее
ClickHouse в 1.5$\times$. Причины: в ClickHouse
\texttt{shared~data} хранятся внутри строки, что обеспечивает
идеальную локальность при чтении множества редких полей сразу; в
Otterbrix разреженная колонка хранится в отдельной таблице, что
добавляет $O(n_\mathit{sparse})$ работу на хэш-словарь
\texttt{\_id}~$\to$~row\_position. ClickHouse также интенсивно
использует LowCardinality-сжатие для строковых колонок, что даёт
некоторое отставание Otterbrix на строковых данных.

На Q5, где к чтению разреженной колонки добавляется фильтрация,
Otterbrix сокращает разрыв: фильтр применяется к малой
вспомогательной таблице и позволяет обрезать объём обрабатываемых
данных ещё на ранней стадии. Для реальных аналитических сценариев,
включающих нетривиальные предикаты по редким полям, архитектура
Otterbrix демонстрирует более предсказуемое время.

По сравнению с PostgreSQL отрыв увеличивается на запросах с
разреженными полями: на Q4 и Q5 Otterbrix быстрее в 18$\times$ и
17$\times$ соответственно. Это объясняется тем, что в JSONB каждый
запрос по полю требует полного разбора документа для всех строк,
тогда как Otterbrix обращается только к соответствующей
вспомогательной таблице.

\subsection{Размер данных}

Размер хранения у Otterbrix лишь на 14\% больше, чем у ClickHouse,
и почти в 3$\times$ меньше, чем у PostgreSQL. Небольшой избыток по
сравнению с ClickHouse объясняется накладными расходами на ведение
\texttt{\_id} во вспомогательных таблицах (8~байт на каждую
непустую строку разреженной колонки) и менее агрессивным сжатием
строковых значений в текущей реализации.

\subsection{Производительность вставки}

По времени вставки Otterbrix уступает ClickHouse примерно в
1.5$\times$: более простая реализация сжатия на стороне вставки;
синхронный учёт разреженных колонок в рамках той же транзакции,
что и основная вставка. В ClickHouse продвижение в отдельные
колонки выполняется фоновыми merge-процессами.

По сравнению с PostgreSQL отрыв по вставке составляет
4.5$\times$~--- существенное преимущество для сценариев с
интенсивной записью (логирование, телеметрия).

\section{Что достигнуто}

По итогам работы получена практически работоспособная реализация
со следующими характеристиками:
\begin{enumerate}
    \item Производительность, сопоставимая с ClickHouse, на
    типичных аналитических запросах (до 1.5$\times$ по отдельным
    показателям, 20--30\% по большинству).
    \item Производительность, существенно превосходящая PostgreSQL
    (в 10--20$\times$ по всем рассмотренным запросам).
    \item Компактное хранение, сопоставимое с ClickHouse, и в
    3$\times$ лучше, чем JSONB в PostgreSQL.
    \item Новый способ хранения JSON в отдельных двухколоночных
    таблицах~--- оригинальный подход, сочетающий преимущества
    колоночного представления и EAV.
    \item Переиспользование существующих механизмов реляционного
    движка: всё хранилище построено на обычных колоночных
    таблицах, что даёт автоматическое распространение всех
    оптимизаций (векторизация, zone~maps, индексы, MVCC, WAL) на
    разреженные колонки без дополнительных усилий.
    \item Избегание низкоуровневых проблем: не пришлось
    проектировать отдельную систему хранения для разреженных
    данных; всё опирается на стандартный колоночный интерфейс.
\end{enumerate}

\section{Ограничения и направления будущей работы}

Реализация имеет ряд ограничений, которые могут быть сняты в
будущих итерациях:

\begin{itemize}
    \item \textbf{Перевод реконструкции SELECT на явные LEFT~JOIN.}
    В текущей реализации соединение с вспомогательными таблицами
    выполняется в пост-обработчике диспетчера, минуя логический
    план. Перевод этой операции на узлы LEFT~JOIN дал бы
    применимость стандартных оптимизаций (порядок соединений,
    push-down предикатов через JOIN) и единообразие EXPLAIN.
    \item \textbf{Адаптивный порог
    \texttt{sparse\_threshold}.} Возможна эвристика, которая
    корректирует порог на основе реального распределения частот в
    таблице.
    \item \textbf{Обратная миграция.} Перенос колонки из
    promoted обратно в sparse в сценариях с <<взрывом>> активности
    одного поля с последующим затуханием.
    \item \textbf{Удаление неиспользуемых разреженных таблиц.}
    Сжатие и выгрузка неактивных вспомогательных таблиц.
    \item \textbf{Специализированные индексы для разреженных
    таблиц.} B-дерево по \texttt{\_id} для ускорения LEFT~JOIN.
    \item \textbf{Распределённая репликация.} Шардирование
    вспомогательных таблиц по \texttt{\_id} синхронно с основной
    таблицей.
\end{itemize}

\chapterconclusion

Результаты сравнительного тестирования подтверждают, что
предложенная архитектура обеспечивает производительность,
конкурентоспособную с промышленным лидером (ClickHouse), и
значительно превосходящую классическое решение в PostgreSQL с
JSONB. Ключевое преимущество подхода~--- в естественной интеграции с
существующими механизмами колоночного реляционного движка:
разреженные таблицы являются обычными таблицами, автоматически
получают все оптимизации, правильно интегрируются с MVCC, WAL и
индексами. В отличие от ClickHouse, где редкие пути хранятся в
специальном внутреннем формате с ограниченной функциональностью,
наше решение сохраняет для таких полей полный набор операций и
оптимизаций.
