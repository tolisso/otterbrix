\chapter{Проектирование решения}

\section{Общая идея}

Изучение существующих подходов привело к следующей комбинации
идей, которая и составляет архитектурное ядро настоящей работы.

\textbf{Основная таблица} хранит данные по колоночной схеме,
аналогичной классическим реляционным колоночным СУБД. Каждое поле,
которое хотя бы с некоторой частотой присутствует в поступающих
документах, становится физической колонкой основной таблицы со
всеми стандартными свойствами колоночного хранения: сжатием,
zone~maps, пакетным сканированием, индексами, векторизованным
исполнением предикатов.

\textbf{Вспомогательные таблицы} создаются для полей, которые
встречаются редко. Для каждого такого поля заводится отдельная
двухколоночная таблица вида:
\begin{verbatim}
CREATE TABLE db.main__sp__<field>__<type> (
  _id BIGINT NOT NULL,
  value <type>
);
\end{verbatim}
В эту таблицу записываются только те строки, для которых исходное
поле было заполнено. Идентификатор \texttt{\_id} связывает строку
вспомогательной таблицы со строкой основной таблицы, в которой это
поле было встречено.

\textbf{Операция SELECT} восстанавливает полную строку как
LEFT~JOIN основной таблицы и всех вспомогательных таблиц,
упомянутых в запросе. LEFT~JOIN обеспечивает то же пользовательское
поведение, что и колоночная таблица с NULL-значениями: отсутствующие
во вспомогательной таблице идентификаторы дают NULL в результирующей
ячейке.

\textbf{Продвижение} поля из разреженного режима в основную таблицу
происходит автоматически при достижении порога заполненности. Когда
число ненулевых значений, накопленных во вспомогательной таблице,
превышает заданный при создании основной таблицы порог
\texttt{sparse\_threshold}, система выделяет физическую колонку в
основной таблице, переносит данные из вспомогательной таблицы в
соответствующие строки основной, удаляет вспомогательную таблицу, и
дальнейшие вставки этого поля идут сразу в основную таблицу.

\section{Формализация модели}

Введём обозначения: $T$~--- основная таблица; $N$~--- число строк в
ней; $\mathcal{F}~=~\{f_1, \ldots, f_k\}$~--- множество JSON-путей,
встреченных хотя бы раз; $n_i$~--- число строк, в которых поле
$f_i$ было заполнено ненулевым значением; $\theta$~--- заранее
зафиксированный порог продвижения.

Состояние каждого поля $f_i$ определяется одним из трёх статусов:
\begin{itemize}
    \item \textbf{Pinned (закреплённое).} Указывается явно при
    \texttt{CREATE TABLE} через параметр \texttt{pinned\_columns}.
    Такое поле всегда хранится в основной таблице, независимо от
    статистики заполненности.
    \item \textbf{Sparse (разреженное).} $n_i<\theta$. Поле
    хранится только во вспомогательной таблице.
    \item \textbf{Promoted (продвинутое).} $n_i\geq\theta$. Поле
    хранится в основной таблице. Повторное <<вытеснение>> в
    разреженное состояние не предусмотрено: продвижение
    однонаправленное.
\end{itemize}

Переход из sparse в promoted фиксируется атомарно в момент первого
\textsc{insert}, после которого $n_i\geq\theta$. С этого момента все
новые значения поступают напрямую в основную таблицу, а ранее
накопленные во вспомогательной таблице значения мигрируют одной
операцией.

\section{Обоснование формы хранения}

\subsection{Отдельная таблица вместо внутреннего формата}

Центральное архитектурное решение~--- хранить разреженные поля в
полноценных двухколоночных таблицах, а не в специальном внутреннем
формате (как \texttt{shared~data} в ClickHouse). Аргументы в пользу
этого выбора:

\begin{itemize}
    \item \textbf{Переиспользование всей реляционной машинерии.}
    Любая оптимизация, применяемая к основной таблице
    (zone~maps, векторизация, projection~pushdown, индексы,
    сжатие), автоматически применима и к вспомогательной таблице.
    Не требуется писать специализированный код для разреженного
    хранилища.
    \item \textbf{Совместимость с MVCC и WAL.} Операции над
    вспомогательной таблицей проходят по тому же пути, что и над
    основной, автоматически получая транзакционные гарантии и
    журналирование.
    \item \textbf{Простота отладки и диагностики.}
    Вспомогательная таблица~--- это обычная таблица; её можно
    посмотреть отдельным \textsc{select}, проверить содержимое,
    оценить размер, применить EXPLAIN.
    \item \textbf{Возможность независимой оптимизации.}
    Вспомогательная таблица может иметь собственный индекс по
    \texttt{\_id} (например, zone~map по \texttt{\_id} полезен
    при выборочных предикатах по основной таблице с последующим
    JOIN).
\end{itemize}

\subsection{Ключ \texttt{\_id} вместо позиции строки}

Альтернатива~--- использовать физический номер строки
(row~position) как ключ связи. Отбрасывается по причинам
устойчивости к операциям над основной таблицей (физическая позиция
может меняться при сжатии, ребалансировке row~groups, перестройке
индексов; логический \texttt{\_id} остаётся стабильным) и
отсутствия кросс-зависимостей (вспомогательная таблица не должна
знать о физическом расположении строк в основной; это упрощает
параллельную обработку~--- \textsc{insert} в основную и
вспомогательные таблицы могут идти одновременно, как только известен
\texttt{\_id}).

Идентификаторы \texttt{\_id} генерируются монотонно: для каждой
операции \textsc{insert} система запрашивает у основной таблицы
текущее число строк, присваивает вставляемым строкам
последовательный диапазон $[\texttt{start\_id},
\texttt{start\_id}+|C|)$, и этот диапазон далее используется как
ключ связи.

\subsection{LEFT~JOIN вместо специального оператора}

Чтение данных с разреженными полями реализовано как логическая
операция LEFT~JOIN основной таблицы и вспомогательных таблиц, а не
как специализированная операция гибридного сканирования. Мотивы:

\begin{itemize}
    \item \textbf{Отсутствие нового оператора в физическом плане.}
    LEFT~JOIN~--- стандартный оператор; весь код исполнителя
    (hash~join, merge~join, оптимизатор) уже работает с ним.
    \item \textbf{Автоматический выигрыш от оптимизаций JOIN.}
    Хэш-джойн со словарём \texttt{\_id}~$\to$~row\_position
    выполняется за время, линейное от суммы размеров таблиц.
    \item \textbf{Явность плана для EXPLAIN.}
\end{itemize}

Важный нюанс текущей реализации: физически LEFT~JOIN для
реконструкции разреженных колонок сейчас не создаётся в логическом
плане; эквивалентная семантика достигается на уровне диспетчера
через специализированный пост-процессор результата. Этот компромисс
обсуждается в главе~\ref{ch:impl} и в выводах.

\section{Когда стоит делать колонку разреженной}

Практически ключевой параметр~--- порог $\theta$. От его выбора
зависит баланс между стоимостью чтения разреженного поля (LEFT~JOIN
обычно дороже прямого чтения из основной таблицы), стоимостью
хранения редких полей в основной таблице, и стоимостью добавления
новой колонки при продвижении ($O(N)$ операция, блокирующая
дальнейшие вставки до завершения).

Рассмотрим три стратегии выбора $\theta$.

\subsection{Статический порог при CREATE TABLE}

В реализации используется именно этот подход: параметр
\texttt{sparse\_threshold} указывается однократно и далее остаётся
неизменным. Достоинства: предсказуемость, простота реализации,
отсутствие оверхеда на мониторинг. Недостатки: требует знания
характеристик данных; не адаптируется к изменению статистики.

Эмпирически для типовых полуструктурированных данных оптимальный
порог $\theta$ составляет от 1\% до 10\% от общего числа строк. В
реализации и бенчмарках используется $\theta~=~N/10$.

\subsection{Адаптивный порог}

Альтернативный вариант~--- вычислять $\theta$ на основе текущей
статистики таблицы (например, как медиану или 90-й перцентиль
частот). Отбрасывается в настоящей работе по причинам высокой
стоимости пересчёта и нестабильности поведения: последовательные
\textsc{insert} над одной таблицей при адаптивном пороге могут
давать разные планы исполнения запросов.

\subsection{Ручное указание pinned-колонок}

Отдельный механизм~--- при \texttt{CREATE TABLE} явно указать
список полей, которые всегда попадают в основную таблицу независимо
от статистики. Полезно, когда аналитик заранее знает, что
определённые поля будут интенсивно использоваться в запросах.

Реализация поддерживает оба механизма одновременно: pinned-колонки
создаются сразу как полноценные колонки основной таблицы; остальные
поля подчиняются обычной логике порога $\theta$.

\section{Переход между режимами}

Переход из sparse в promoted~--- самая тяжёлая операция в системе.
Её стоимость складывается из трёх компонентов:
\begin{enumerate}
    \item Добавление физической колонки в основную таблицу
    (\texttt{storage\_add\_column}). На уровне row~groups~---
    создание нового буфера значений и заполнение его значениями по
    умолчанию для всех существующих строк. Время $O(N)$.
    \item Миграция значений из вспомогательной таблицы. Полное
    сканирование вспомогательной таблицы, построение словаря
    \texttt{\_id}~$\to$~value, проход по row~groups основной
    таблицы с подстановкой значений. Время $O(n_i+N)$.
    \item Удаление вспомогательной таблицы~--- относительно
    дёшево.
\end{enumerate}

Суммарное время продвижения составляет $O(N)$~--- преимущественно
за счёт аллокации и инициализации нового буфера для всех
существующих строк. Для таблицы в 10~млн строк при плотном типе
(BIGINT) это порядка 80~МБ инициализации~--- операция измеряется
миллисекундами на современном оборудовании.

Обратный переход не реализован: если поле было продвинуто, оно
остаётся в основной таблице, даже если после этого наполненность
падает. Мотивы: обратный переход несимметричен (требует удаления
колонки, что также $O(N)$), условия для такого перехода редки,
блокировка таблицы была бы заметной.

\section{Плюсы и минусы подхода}

\textbf{Преимущества:}
\begin{enumerate}
    \item Колоночная производительность на часто используемых
    полях: после продвижения поле ничем не отличается от обычной
    колонки.
    \item Компактное хранение редких полей: вспомогательные
    таблицы содержат только фактически заполненные строки.
    \item Автоматическая эволюция схемы: не требуется ручного
    переопределения структуры при появлении новых полей.
    \item Отсутствие специальных структур данных: вспомогательная
    таблица~--- это обычная колоночная таблица.
    \item Отсутствие переписывания основной таблицы при добавлении
    нового поля, если оно остаётся разреженным.
    \item Стабильная семантика \texttt{\_id}: внешние индексы и
    ссылки на строки устойчивы к внутренним операциям движка
    хранения.
\end{enumerate}

\textbf{Недостатки и компромиссы:}
\begin{enumerate}
    \item Чтение разреженного поля дороже чтения основной колонки:
    LEFT~JOIN вносит накладные расходы порядка $O(n_i)$ операций
    хэширования на запрос.
    \item Продвижение~--- блокирующая операция: в течение времени
    продвижения последующие \textsc{insert} в продвигаемое поле
    приостанавливаются.
    \item Выбор порога~--- чувствительный параметр: неправильный
    $\theta$ приводит либо к раздуванию основной таблицы, либо к
    неприемлемой стоимости запросов по редким полям.
    \item Отсутствие обратного перехода.
    \item Число вспомогательных таблиц может расти значительно.
    При 10~000 уникальных путей до достижения порогов возникнет
    10~000 физических таблиц в каталоге; каждая потребляет некоторый
    объём памяти на метаданные.
\end{enumerate}

\section{Псевдокод INSERT}

Для формализации опишем \textsc{insert} в таблицу с вычисляемой
схемой в виде псевдокода (листинг~\ref{lst:insert}).

\begin{algorithm}[!h]
\caption{Алгоритм \textsc{insert} в таблицу с вычисляемой схемой}
\label{lst:insert}
\begin{algorithmic}
  \Function{Insert}{row-chunk $C$, схема $S$}
    \State $\mathtt{start\_id} \gets$ число строк $T$
    \State добавить к $C$ колонку $\_id$ со значениями
      $[\mathtt{start\_id}, \mathtt{start\_id}+|C|)$
    \State $\mathtt{main\_chunk} \gets [\_id]$
    \State $\mathtt{sparse\_chunks} \gets \emptyset$
    \ForAll{колонок $c_j$ из $C$}
      \State $S.\mathrm{append}(f_j, t_j)$
      \State $\mathit{phys} \gets \mathrm{storage\_column\_name}(f_j, t_j)$
      \If{$S.\mathrm{status}(\mathit{phys}) \neq \mathrm{sparse}$}
        \State добавить $c_j$ к $\mathtt{main\_chunk}$
      \Else
        \ForAll{строк $i \in [0, |C|)$}
          \If{$c_j[i] \neq \mathrm{NULL}$}
            \State $\mathtt{sparse\_chunks}[\mathit{phys}]$
              $\gets (\mathtt{start\_id}+i, c_j[i])$
          \EndIf
        \EndFor
        \State $S.\mathrm{increment\_non\_null}(\mathit{phys}, \mathrm{cnt})$
        \If{$S.\mathrm{count}(\mathit{phys}) \geq \theta$}
          \State добавить $\mathit{phys}$ как колонку к $T$
          \State мигрировать sparse-таблицу в $T$
          \State удалить sparse-таблицу
        \EndIf
      \EndIf
    \EndFor
    \State выполнить \textsc{insert} в $T$ с $\mathtt{main\_chunk}$
    \ForAll{($\mathit{phys}, \mathrm{pairs}$) из $\mathtt{sparse\_chunks}$}
      \State выполнить \textsc{insert} в sparse-таблицу $\mathit{phys}$
    \EndFor
  \EndFunction
\end{algorithmic}
\end{algorithm}

Параллельность данного алгоритма обсуждается в главе~\ref{ch:impl}.
Алгоритмическая модель \textsc{select} аналогична и сводится к
скану основной таблицы с последующим присоединением
вспомогательных таблиц по \texttt{\_id} для каждого упомянутого в
запросе sparse-поля.

\chapterconclusion

Предложенная модель хранения сочетает сильные стороны колоночного
представления (для часто используемых полей) и разреженного EAV
(для редких полей), обходя ключевые ограничения каждого из подходов.
Центральные архитектурные решения~--- хранение разреженных полей в
отдельных двухколоночных таблицах, связанных через стабильный
логический идентификатор \texttt{\_id}, а также автоматическое
продвижение полей между режимами при пересечении заранее
зафиксированного порога плотности~--- позволяют достичь приемлемого
баланса между стоимостью хранения, стоимостью чтения и сложностью
реализации.
