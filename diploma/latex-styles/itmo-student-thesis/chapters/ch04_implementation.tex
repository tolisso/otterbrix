\chapter{Реализация}\label{ch:impl}

Настоящая глава описывает реализацию предложенной в главе~3 схемы
хранения в кодовой базе Otterbrix. Основная цель раздела~--- показать,
как архитектурные решения отображаются на конкретные компоненты
кода, и какие структурные изменения потребовалось внести в
различные подсистемы.

\section{Обзор затронутых компонентов}

Реализация задействует следующие ключевые подсистемы Otterbrix:

\begin{itemize}
    \item \texttt{components/catalog/}~--- метаданные таблиц.
    Введён новый класс \texttt{computed\_schema}, отвечающий за
    динамическую схему и статус разреженных колонок.
    \item \texttt{services/dispatcher/}~--- центральная точка
    маршрутизации запросов. Расширен \textsc{insert}- и
    \textsc{select}-путями для таблиц с вычисляемой схемой.
    \item \texttt{services/disk/}~--- менеджер дискового
    хранилища. Добавлена поддержка создания, удаления и миграции
    вспомогательных таблиц.
    \item \texttt{components/sql/transformer/}~--- SQL-трансформер.
    Добавлена поддержка синтаксиса \texttt{CREATE TABLE db.t~();} и
    \texttt{INSERT \ldots\ VALUES (json('\ldots'))}.
    \item \texttt{components/logical\_plan/}~--- узлы логического
    плана. Расширены \texttt{node\_create\_collection\_t}
    параметрами \texttt{sparse\_threshold} и
    \texttt{pinned\_columns}.
    \item \texttt{components/table/}~--- низкоуровневое колоночное
    хранилище. Расширена поддержка операции \texttt{add\_column}.
    \item \texttt{components/vector/}~--- операции над векторами
    значений. Добавлены placeholder-векторы для поддержки
    разреженных \texttt{data\_chunk}.
\end{itemize}

\section{Класс представления вычисляемой схемы}

Класс \texttt{computed\_schema}
(\texttt{components/catalog/computed\_schema.hpp}/.cpp)
инкапсулирует весь учёт метаданных таблицы с вычисляемой схемой.

\subsection{Поля состояния}

Класс \texttt{computed\_schema} хранит следующее состояние:

\begin{itemize}
    \item отображение имени поля в перечень типов, в которых оно
    встречалось;
    \item упорядоченный список пар <<имя поля~--- тип>> в порядке
    их первого появления;
    \item числовой порог продвижения; нулевое значение отключает
    режим разреженного хранения;
    \item счётчики числа ненулевых значений по каждому физическому
    имени колонки;
    \item флаги разреженности по каждому физическому имени:
    истина означает, что колонка всё ещё хранится во вспомогательной
    таблице;
    \item упорядоченный список колонок, продвинутых из разреженного
    состояния в основную таблицу;
    \item множество имён полей, объявленных закреплёнными при
    \texttt{CREATE TABLE};
    \item список колонок, впервые зарегистрированных в текущей
    операции \textsc{insert} как закреплённые,~--- буфер для
    последующего создания соответствующих физических колонок в
    основной таблице.
\end{itemize}

Центральное понятие~--- физическое имя колонки (\texttt{phys\_name}),
формируемое по правилу
\texttt{\_\_<field\_name>\_\_<type\_enum>}. Два префикса подчёркивания
зарезервированы для служебных колонок и гарантируют, что
автоматически порождённые имена не конфликтуют с именами, которые
пользователь может ввести явно. Число (тип) в суффиксе необходимо
потому, что одна и та же логическая колонка может существовать в
нескольких типах: если первый \textsc{insert} вставил
\texttt{\{"price":~100\}}, а следующий~--- \texttt{\{"price":~"free"\}},
в схеме появляются две отдельные физические колонки
\texttt{\_\_price\_\_INT64} и \texttt{\_\_price\_\_STRING}.

\subsection{Центральные операции}

\begin{description}
    \item[\texttt{append(field\_name, type)}] Регистрирует новую
    пару (field, type) в схеме, если её ещё нет. Определяет
    начальный статус колонки: pinned сразу становится promoted и
    добавляется в \texttt{newly\_pinned\_}; в остальных случаях
    при \texttt{sparse\_threshold\_~>~0} колонка получает статус
    sparse; иначе~--- promoted.
    \item[\texttt{increment\_non\_null(phys\_name, count)}]
    Увеличивает счётчик ненулевых значений. Возвращает
    \texttt{true}, если после инкремента колонка пересекла порог
    и должна быть продвинута.
    \item[\texttt{latest\_types\_struct()}] Возвращает полную
    актуальную схему таблицы в виде структурного типа. Исключает
    колонки, всё ещё находящиеся в разреженном состоянии; при
    включённом разреженном режиме предпосылает служебную колонку
    \texttt{\_id BIGINT}.
    \item[\texttt{sparse\_table\_name(coll, field, type)}]
    Генерирует имя вспомогательной таблицы по паттерну
    \texttt{<coll>\_\_sp\_\_<field>\_\_<type>}.
\end{description}

\subsection{Потокобезопасность}

Текущая реализация \texttt{computed\_schema} синхронизируется
внешним блокирующим мьютексом на уровне каталога
(\texttt{catalog\_mutex\_} в \texttt{catalog::catalog}). Каждое
изменение схемы~--- регистрация нового поля, увеличение счётчика,
продвижение~--- выполняется под эксклюзивной блокировкой. Введение
более мелкозернистых блокировок на уровне \texttt{computed\_schema}
не дало бы заметного выигрыша, так как \textsc{insert} в одну и ту
же таблицу уже сериализуются на уровне диспетчера вследствие
необходимости атомарного получения \texttt{start\_id}.

\section{Диспетчер: обработка INSERT}

Основной путь \textsc{insert} для таблиц с вычисляемой схемой
реализован в \texttt{services/dispatcher/dispatcher.cpp}.
Ветвление происходит в обработчике узла логического плана
\texttt{insert\_t}: если каталог сообщает
\texttt{catalog\_.table\_computes(id)}, выбирается
специализированный путь.

\subsection{Разреженный путь}

Алгоритмически путь повторяет псевдокод из главы~3.

\textbf{Шаг~1. Получение \texttt{start\_id}.} Отправляется
асинхронное сообщение
\texttt{manager\_disk\_t::storage\_total\_rows} дисковому
менеджеру. Оператор \texttt{co\_await} приостанавливает выполнение
до получения ответа.

\textbf{Шаг~2. Итерация по колонкам входного чанка.} Для каждой
колонки \texttt{col} вычисляется
\texttt{field\_name = col.type().alias()} (имя колонки хранится
как alias типа), затем \texttt{phys\_name}. Вызов
\texttt{schema.append(\ldots)} регистрирует колонку.

\textbf{Шаг~3. Классификация.} Проверка
\texttt{schema.is\_sparse(phys\_name)}:
\begin{itemize}
    \item Если sparse: цикл по строкам с формированием пар
    \texttt{(start\_id~+~row\_idx, value)} для ненулевых строк.
    Пары накапливаются в структуру \texttt{sparse\_entry\_t}.
    \item Если не sparse: колонка добавляется в
    \texttt{promoted\_cols}.
\end{itemize}
После цикла \texttt{schema.increment\_non\_null(\ldots)}
вызывается для детекции продвижения. Если продвижение произошло,
информация помещается в вектор \texttt{just\_promoted}.

\textbf{Шаг~4. Первые вставки pinned-колонок.} Вызов
\texttt{schema.take\_newly\_pinned()} возвращает список
pinned-колонок, впервые зарегистрированных в этой операции. Для
каждой отправляется \texttt{manager\_disk\_t::storage\_add\_column}.

\textbf{Шаг~5. Формирование чанка для основного \textsc{insert}.}
Оригинальный \texttt{chunk.data} очищается и заполняется заново:
добавляется колонка \texttt{\_id} с последовательностью, затем все
элементы \texttt{promoted\_cols}.

\textbf{Шаг~6. Создание физических колонок для just\_promoted.}
Для каждой продвинутой в этом батче колонки отправляется
\texttt{storage\_add\_column}.

\textbf{Шаг~7. Основной \textsc{insert}.} Вызывается
\texttt{execute\_plan\_impl} с обновлённым чанком.

\textbf{Шаг~8. Запись в разреженные таблицы.} Для каждой
\texttt{sparse\_entry} при необходимости создаётся вспомогательная
таблица (идемпотентно), строится двухколоночный чанк
\texttt{(\_id, value)}, вызывается \texttt{storage\_append}.

\textbf{Шаг~9. Миграция just\_promoted.} Для каждой продвинутой
колонки: полное сканирование основной таблицы с построением
словаря \texttt{\_id}~$\to$~row\_position; полное сканирование
вспомогательной таблицы и патчинг значений через
\texttt{storage\_patch\_column}; удаление вспомогательной таблицы.

\subsection{Неразреженный путь}

При \texttt{sparse\_threshold~==~0} вычисляемая схема не
использует разреженное хранение. Путь существенно проще: для
каждой колонки входного чанка выполняется \texttt{schema.append},
при отсутствии колонки в физической схеме~---
\texttt{storage\_add\_column}, затем стандартный \textsc{insert}.

\section{Диспетчер: обработка SELECT}

\textsc{select}-путь для таблицы с разреженными колонками
реализован как пост-обработка результата основного запроса:

\begin{enumerate}
    \item Основной запрос исполняется стандартным образом над
    основной таблицей. Результат~--- обычный \texttt{data\_chunk\_t}
    с колонками основной таблицы, включая служебную \texttt{\_id}.
    \item Если в SQL-запросе упоминаются поля, которые на момент
    выполнения являются разреженными, диспетчер добавляет к
    результату дополнительные колонки:
    \begin{enumerate}
        \item Поиск колонки \texttt{\_id}~--- её позиция как ключ связи.
        \item Построение словаря
        \texttt{\_id}~$\to$~позиция строки в результате
        ($O(n)$ времени и памяти).
        \item Для каждой запрошенной разреженной колонки:
        сканирование соответствующей вспомогательной таблицы,
        создание нового \texttt{vector\_t} с маской валидности
        <<всё NULL>>, итерация по строкам sparse-таблицы с
        записью значений в результирующий вектор по найденным
        позициям.
    \end{enumerate}
\end{enumerate}

Такая реализация функционально эквивалентна LEFT~JOIN основной и
вспомогательных таблиц, но избегает создания полноценного плана
JOIN. Это упрощает кодовую базу на текущем этапе, однако оставляет
открытым вопрос о применимости оптимизаций JOIN. Перевод
\textsc{select}-пути на явные узлы LEFT~JOIN в логическом плане
обсуждается в главе~\ref{ch:results} как направление будущей работы.

\section{SQL-трансформер}

\subsection{Создание таблицы с вычисляемой схемой}

Для создания таблицы с вычисляемой схемой используется синтаксис с
пустым списком колонок. SQL-трансформер
(\texttt{components/sql/transformer/impl/transform\_table.cpp})
распознаёт \texttt{CreateStmt} с пустым \texttt{tableElts} и создаёт
\texttt{node\_create\_collection\_t} с флагом
\texttt{has\_dynamic\_schema=true}. Параметры разреженного хранения
передаются через опциональный синтаксис WITH:
\begin{verbatim}
CREATE TABLE db.t ()
  WITH (sparse_threshold = 10000);
CREATE TABLE db.t ()
  WITH (sparse_threshold = 10000,
        pinned_columns = 'commit.rev,commit.operation');
\end{verbatim}

\subsection{Вставка JSON-документов одним выражением}

Этот синтаксис предоставляет удобный способ вставки JSON-документов
напрямую из SQL. SQL-трансформер детектирует конструкцию
\texttt{json('\ldots')} как вызов функции (FuncCall) с одним
строковым аргументом в контексте VALUES-строки без указания списка
колонок \textsc{insert}. При обнаружении такой конструкции
активируется путь \texttt{build\_json\_insert}:
\begin{enumerate}
    \item Каждая VALUES-строка разбирается как JSON-документ через
    библиотеку Boost.JSON.
    \item JSON рекурсивно <<расплющивается>>: вложенные объекты
    порождают пути с точечной нотацией (\texttt{user.profile.age}),
    массивы сериализуются обратно в JSON-строки, null-значения
    пропускаются.
    \item По всему батчу строится объединение путей. Для каждого
    пути определяется тип на основании первого ненулевого значения.
    \item Создаётся \texttt{data\_chunk\_t} с колонками по числу
    уникальных путей; для каждой строки проставляются значения
    найденных в ней полей.
    \item Формируется \texttt{node\_insert\_t}, который далее идёт
    в диспетчер и попадает в стандартный путь \textsc{insert} для
    вычисляемой схемы.
\end{enumerate}

\section{Модификации подсистемы хранения}

Ключевое изменение в \texttt{services/disk/manager\_disk.hpp}~---
введение операции \texttt{storage\_add\_column(collection\_name,
column\_definition)}. Реализация делегируется
\texttt{data\_table\_t::add\_column}, которая создаёт новый объект
таблицы, в котором сохраняются ссылки на существующие колоночные
буферы (shared\_ptr-семантика), выделяется новый буфер для
добавляемой колонки с ёмкостью, равной текущему числу строк, и
буфер заполняется значениями по умолчанию.

Важный аспект: старые колонки не копируются; новый
\texttt{data\_table\_t} просто разделяет их с родительским.
Единственная $O(N)$ работа~--- это инициализация буфера новой
колонки.

\section{Параллельность и корректность}

Работа с разреженными таблицами в Otterbrix корректно встраивается
в существующую акторную модель параллельного исполнения:

\begin{itemize}
    \item \textbf{Параллельность между таблицами.} \textsc{insert}
    и \textsc{select} в разные коллекции обрабатываются
    независимыми акторами и не создают взаимных блокировок.
    \item \textbf{Параллельность между \textsc{insert} и
    \textsc{select} в одной таблице.} Действующий MVCC-протокол
    основной таблицы распространяется и на вспомогательные:
    \textsc{select} видит снимок состояния на момент начала
    транзакции, в том числе для разреженных колонок, так как все
    записи во вспомогательные таблицы выполняются в рамках той же
    транзакции, что и основной \textsc{insert}.
    \item \textbf{Сериализация \textsc{insert} в одну таблицу.}
    \textsc{insert} сериализуются на уровне получения
    \texttt{start\_id}: два параллельных \textsc{insert} запрашивают
    \texttt{start\_id} у актёра дискового менеджера, и этот актёр
    обеспечивает атомарное выделение непересекающихся диапазонов
    идентификаторов.
    \item \textbf{Атомарность продвижения.} Продвижение выполняется
    в рамках одной транзакции. Если продвижение обнаруживает
    конфликт (например, параллельная сессия уже продвинула ту же
    колонку), операция корректно отменяется и повторяется.
\end{itemize}

Совокупно система обеспечивает согласованность в духе
snapshot~isolation: каждая транзакция видит консистентное состояние
таблицы, включая разреженные колонки, независимо от параллельных
операций.

\section{Тестовое покрытие}

Для реализации разработано обширное тестовое покрытие, включающее:

\begin{itemize}
    \item \textbf{Модульные тесты}~--- проверка корректности
    \texttt{computed\_schema} в изоляции; распознавание SQL-
    конструкций \texttt{CREATE TABLE db.t~()} и
    \texttt{INSERT \ldots\ VALUES (json(\ldots))}.
    \item \textbf{Интеграционные тесты}~--- более 30~сценариев:
    базовый \textsc{insert}/\textsc{select} с автоматической
    эволюцией схемы; эволюция между батчами; разреженное хранение;
    продвижение с миграцией данных; pinned-колонки; запросы,
    смешивающие плотные и разреженные поля; граничные случаи.
    \item \textbf{Тесты производительности}~--- сравнение трёх
    конфигураций Otterbrix между собой и с DuckDB на стандартном
    датасете JSONBench.
\end{itemize}

Полный прогон всех тестов в конфигурации Debug занимает около
50~секунд и насчитывает свыше 470~тестовых сценариев. Все тесты на
момент завершения работы проходят успешно.

\chapterconclusion

Реализация предложенной архитектуры потребовала введения нового
класса метаданных \texttt{computed\_schema}, расширения пути
обработки \textsc{insert} в диспетчере сложной последовательностью
действий (классификация колонок, параллельная запись в основную и
вспомогательные таблицы, миграция продвинутых колонок), расширения
пути обработки \textsc{select} пост-обработчиком,
реконструирующим разреженные колонки, расширения SQL-трансформера
поддержкой динамического \texttt{CREATE TABLE} и
\texttt{INSERT \ldots\ VALUES (json(\ldots))}, и минимальных правок
низкоуровневых подсистем хранения. Интеграция с существующей
акторной моделью параллелизма не потребовала введения новых
механизмов синхронизации.
