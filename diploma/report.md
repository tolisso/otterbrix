## 1. Цели и задачи практики

Целью практики являлось получение навыков разработки высокопроизводительного ПО на C++ в контексте создания СУБД. Практика проходила в рамках проекта с открытым исходным кодом Otterbrix.

Задачи практики:

1. Ознакомление с архитектурой Otterbrix: колоночное хранилище, исполнение запросов, оптимизатор.
2. Разработка оптимизации чтения только необходимых колонок (column pruning).
3. Разработка типизированных операторов фильтрации с компиляцией под конкретные типы данных.
4. Векторизация операторов для ускорения через попадание в кэш процессора.
5. Реализация SQL-оператора вставки JSON-документов для таблиц с динамической схемой.
6. Подготовка отчетных документов.

## 2. Сведения об организации

Otterbrix -- проект с открытым исходным кодом (https://github.com/otterbrix/otterbrix), представляющий собой вычислительный фреймворк для обработки полуструктурированных данных. Система объединяет транзакционную обработку с аналитикой, поддерживает колоночное хранилище и динамическую схему, совместима с SQL-синтаксисом PostgreSQL. Написан на C++20 с использованием акторной модели, корутин и менеджера пакетов Conan 2.

---

## 3. Цели проекта

1. **Сокращение объема чтения с диска.** При `SELECT a, b FROM t WHERE c > 10` ранее считывались все колонки. Цель -- читать только a, b, c.
2. **Ускорение фильтрации.** Устранить динамическую диспетчеризацию типов на каждой строке, компилируя предикаты заранее.
3. **Улучшение кэш-эффективности.** Перейти от построчной к пакетной обработке (блоки по 1024 строки).
4. **Удобный интерфейс вставки JSON.** Создать синтаксис `INSERT INTO t VALUES (json('{...}'))` с автоматическим выводом схемы.

## 5. Описание выполненного проекта

### 5.1. Column Pruning

Реализован проход оптимизатора `column_pruning` (`components/planner/optimizer/rules/column_pruning.cpp`), который после валидации схемы обходит логический план, собирает индексы колонок из SELECT и WHERE, и записывает результат в `node_aggregate_t::projected_cols`. Операторы сканирования создают `data_chunk_t` с placeholder-векторами для непрочитанных колонок, сохраняя стабильность индексов. Для JOIN-запросов индексы разделяются по сторонам с учетом условий соединения. Покрыто 8 интеграционными тестами.

### 5.2. Типизированные предикаты и векторизация

Оператор фильтрации переведен с построчного сравнения через виртуальные вызовы на типизированные предикаты, компилируемые до начала сканирования. Вместо построчного копирования результатов оператор собирает индексы совпавших строк в `indexing_vector_t`, затем выполняет пакетное копирование. Операторы сканирования работают с `data_chunk_t` фиксированного размера (1024 строки), обеспечивая попадание данных в кэш L1.

### 5.3. SQL-оператор вставки JSON

Реализован синтаксис `INSERT INTO t VALUES (json('{...}')), (json('{...}'))`. SQL-трансформер (`transform_insert.cpp`) обнаруживает вызовы `json(...)`, хелпер `json_insert.cpp` парсит и расплющивает JSON через Boost.JSON (вложенные объекты -> пути через точку). По всем документам батча строится union-схема, создается `data_chunk_t` с NULL для отсутствующих полей. Dispatcher автоматически выполняет эволюцию схемы. Покрыто 2 модульными и 5 интеграционными тестами.
