# Глава 3. Проектирование решения

## 3.1. Общая идея

Изучение существующих подходов (глава 2) привело к следующей комбинации идей, которая и составляет архитектурное ядро настоящей работы.

**Основная таблица** хранит данные по колоночной схеме, аналогичной классическим реляционным колоночным СУБД. Каждое поле, которое хотя бы с некоторой частотой присутствует в поступающих документах, становится физической колонкой основной таблицы со всеми стандартными свойствами колоночного хранения: сжатием, zone maps, пакетным сканированием, индексами, векторизованным исполнением предикатов.

**Вспомогательные таблицы** создаются для полей, которые встречаются редко. Для каждого такого поля заводится отдельная двухколоночная таблица вида:

```
CREATE TABLE db.main__sp__<field>__<type> (
  _id BIGINT NOT NULL,
  value <type>
);
```

В эту таблицу записываются только те строки, для которых исходное поле было заполнено. Идентификатор `_id` связывает строку вспомогательной таблицы со строкой основной таблицы, в которой это поле было встречено.

**Операция SELECT** восстанавливает полную строку как LEFT JOIN основной таблицы и всех вспомогательных таблиц, упомянутых в запросе (или во всех, при `SELECT *`). LEFT JOIN обеспечивает то же пользовательское поведение, что и колоночная таблица с NULL-значениями: отсутствующие во вспомогательной таблице идентификаторы дают NULL в результирующей ячейке.

**Продвижение** поля из разреженного режима в основную таблицу происходит автоматически при достижении порога заполненности. Когда число ненулевых значений накопленных в вспомогательной таблице превышает заданный при создании основной таблицы порог `sparse_threshold`, система:

1. Выделяет физическую колонку в основной таблице (операция ALTER на уровне движка хранения).
2. Переносит данные из вспомогательной таблицы в соответствующие строки основной (операция миграции).
3. Удаляет вспомогательную таблицу.
4. Дальнейшие вставки этого поля идут сразу в основную таблицу.

## 3.2. Формализация модели

Введём следующие обозначения:

- $T$ — основная таблица с динамической схемой.
- $N$ — число строк в $T$ на данный момент.
- $\mathcal{F} = \{f_1, f_2, \ldots, f_k\}$ — множество JSON-путей, встреченных хотя бы раз за всё время существования $T$.
- Для каждого $f_i$ — $n_i$ число строк, в которых поле $f_i$ было заполнено ненулевым значением.
- $\theta$ — заранее зафиксированный порог продвижения (`sparse_threshold`).

Тогда состояние каждого поля $f_i$ определяется одним из трёх статусов:

- **Pinned (закреплённое).** Указывается явно при `CREATE TABLE` через параметр `pinned_columns`. Такое поле всегда хранится в основной таблице, независимо от статистики заполненности. Используется для полей, заранее известных аналитику как критически важных для запросов.
- **Sparse (разреженное).** $n_i < \theta$. Поле хранится только во вспомогательной таблице.
- **Promoted (продвинутое).** $n_i \geq \theta$. Поле хранится в основной таблице. Повторное «вытеснение» в разреженное состояние не предусмотрено: продвижение однонаправленное.

Переход из sparse в promoted фиксируется атомарно в момент первого INSERT, после которого $n_i \geq \theta$. С этого момента все новые значения поступают напрямую в основную таблицу, а ранее накопленные во вспомогательной таблице значения мигрируют одной операцией.

## 3.3. Обоснование выбора именно такой формы хранения

### 3.3.1. Почему отдельная таблица, а не внутренний формат

Центральное архитектурное решение — хранить разреженные поля в полноценных двухколоночных таблицах, а не в специальном внутреннем формате (как shared data в ClickHouse). Аргументы в пользу этого выбора:

- **Переиспользование всей реляционной машинерии.** Любая оптимизация, применяемая к основной таблице — zone maps, векторизация, проекционная push-down, индексы, сжатие — автоматически применима и к вспомогательной таблице. Не требуется писать специализированный код для разреженного хранилища.
- **Совместимость с MVCC и WAL.** Операции INSERT/UPDATE/DELETE над вспомогательной таблицей проходят по тому же пути, что и над основной, автоматически получая транзакционные гарантии и журналирование.
- **Простота отладки и диагностики.** Вспомогательная таблица — это обычная таблица; её можно посмотреть отдельным SELECT, проверить содержимое, оценить размер, применить EXPLAIN.
- **Возможность независимой оптимизации.** Вспомогательная таблица может иметь собственный индекс по `_id` (например, zone map по `_id` полезен при выборочных предикатах по основной таблице с последующим JOIN).

### 3.3.2. Почему ключ `_id`, а не позиция строки в основной таблице

Альтернатива — использовать физический номер строки (row position) как ключ связи. Отбрасывается по следующим причинам:

- **Устойчивость к операциям над основной таблицей.** Физическая позиция строки может меняться при сжатии, ребалансировке row groups, перестройке индексов. Логический `_id` остаётся стабильным.
- **Отсутствие кросс-зависимостей.** Вспомогательная таблица не должна знать о физическом расположении строк в основной. Это упрощает параллельную обработку (INSERT в основную и вспомогательные таблицы могут идти одновременно, как только известен `_id`).

Идентификаторы `_id` генерируются монотонно: для каждой операции INSERT система запрашивает у основной таблицы текущее число строк, присваивает вставляемым строкам последовательный диапазон `[start_id, start_id + batch_size)`, и этот диапазон далее используется как ключ связи.

### 3.3.3. Почему LEFT JOIN, а не UNION или специальный оператор

Чтение данных с разреженными полями реализовано как логическая операция LEFT JOIN основной таблицы и вспомогательных таблиц, а не как специализированная операция гибридного сканирования. Мотивы:

- **Отсутствие нового оператора в физическом плане.** LEFT JOIN — стандартный оператор; весь код исполнителя (hash join, merge join, оптимизатор) уже работает с ним. Экономия на разработке и на тестировании.
- **Автоматический выигрыш от оптимизаций JOIN.** Хэш-джойн со словарём `_id → row_position` выполняется за время, линейное от суммы размеров таблиц. При этом:
  - Если в основной таблице после фильтрации остаётся мало строк, сканирование вспомогательной таблицы с фильтром `_id IN (...)` работает быстро (при наличии индекса по `_id`).
  - Если во вспомогательной таблице мало строк (именно это типично для sparse-полей), полный скан вспомогательной таблицы и сборка словаря обходится дёшево.
- **Явность плана для EXPLAIN.** Пользователь видит честный план запроса и понимает стоимость каждого этапа.

Важный нюанс текущей реализации: физически LEFT JOIN для reconstruction разреженных колонок сейчас не создаётся в логическом плане; эквивалентная семантика достигается на уровне диспетчера через специализированный пост-процессор результата. Этот компромисс обсуждается в главе 4 и в выводах.

## 3.4. Когда стоит делать колонку разреженной

Практически ключевой параметр — порог $\theta$. От его выбора зависит баланс между:

- стоимостью чтения разреженного поля (LEFT JOIN, как правило, дороже прямого чтения из основной таблицы);
- стоимостью хранения редких полей в основной таблице (пустые строки занимают место в битовой маске валидности и, в зависимости от типа, в буфере значений);
- стоимостью добавления новой колонки при продвижении (O(N) операция, блокирующая дальнейшие вставки до завершения).

Рассмотрим три стратегии выбора $\theta$.

### 3.4.1. Статический порог, заданный при CREATE TABLE

В реализации используется именно этот подход: параметр `sparse_threshold` указывается однократно и далее остаётся неизменным. Достоинства:

- **Предсказуемость.** Пользователь контролирует, в какой момент поле начинает «платить» за полное колоночное хранение.
- **Простота реализации.** Нет необходимости в адаптивных алгоритмах или статистических моделях.
- **Отсутствие оверхеда на мониторинг.** Система не тратит ресурсы на вычисление «оптимального» порога в реальном времени.

Недостатки:

- Требует знания характеристик данных для разумного выбора. Слишком малый порог сводит решение к наивному колоночному хранению (все поля становятся физическими колонками). Слишком большой порог оставляет много данных в разреженных таблицах, удорожая запросы.
- Не адаптируется к изменению статистики: если доминирующее распределение путей меняется во времени, один и тот же порог может стать неоптимальным.

Эмпирически для типовых полуструктурированных данных (логи, события, JSON-телеметрия) оптимальный порог $\theta$ составляет от 1% до 10% от общего числа строк. В реализации и бенчмарках используется $\theta = N/10$ (10% — точка перегиба, при которой стоимость LEFT JOIN начинает превышать стоимость хранения пустой колонки).

### 3.4.2. Адаптивный порог

Альтернативный вариант — вычислять $\theta$ на основе текущей статистики таблицы: например, как медиану или 90-й перцентиль частот встреченных путей. Отбрасывается в настоящей работе по следующим причинам:

- **Стоимость пересчёта.** Перестройка порога при каждом INSERT требует перебора всех полей и, возможно, принятия решений об обратном перемещении ранее продвинутых полей в разреженный режим — крайне дорогая операция.
- **Нестабильность поведения.** Последовательные INSERT над одной таблицей при адаптивном пороге могут давать разные планы исполнения запросов, что затрудняет тестирование и диагностику.

### 3.4.3. Ручное указание pinned-колонок

Отдельный механизм — при `CREATE TABLE` явно указать список полей, которые **всегда** попадают в основную таблицу независимо от статистики. Это полезно, когда аналитик заранее знает, что определённые поля будут интенсивно использоваться в запросах, даже если их фактическая плотность невысока.

Реализация поддерживает оба механизма одновременно: pinned-колонки создаются сразу как полноценные колонки основной таблицы; остальные поля подчиняются обычной логике порога $\theta$.

## 3.5. Переход между режимами

Переход из sparse в promoted — самая тяжёлая операция в системе. Рассмотрим её стоимость и влияние.

**Компоненты операции продвижения:**

1. **Добавление физической колонки в основную таблицу.** Операция `storage_add_column`. На уровне row groups (сегментов колоночной таблицы) — создание нового буфера значений и заполнение его значениями по умолчанию для всех существующих строк. Время O(N), где N — текущее число строк.
2. **Миграция значений из вспомогательной таблицы.** Полное сканирование вспомогательной таблицы, построение словаря `_id → value`, проход по row groups основной таблицы с подстановкой значений. Время O(n_i + N), где n_i — число строк во вспомогательной таблице.
3. **Удаление вспомогательной таблицы.** Операция освобождения ресурсов. Относительно дёшево.

**Суммарное время** продвижения составляет O(N) — преимущественно за счёт аллокации и инициализации нового буфера для всех существующих строк. Для таблицы в 10 млн строк при плотном типе (например, BIGINT) это порядка 80 МБ инициализации — операция измеряется миллисекундами на современном оборудовании.

**Обратный переход не реализован.** То есть, если поле было продвинуто, оно остаётся в основной таблице даже если после этого наполненность падает. Мотивы:

- Обратный переход несимметричен: он требует перестройки основной таблицы с удалением колонки. Основная таблица хранится как неизменяемый (по row groups) объект; удаление колонки в текущей реализации так же требует O(N) работы.
- Условия, при которых обратный переход был бы выгоден, редки: типично поля монотонно насыщаются данными, а не освобождаются.
- Блокировка таблицы во время обратного перехода была бы ещё более заметной, чем при продвижении, так как к нему добавляется перенос данных из колонки в разреженную таблицу.

## 3.6. Анализ плюсов и минусов предложенного подхода

**Преимущества предложенной схемы:**

1. **Колоночная производительность на часто используемых полях.** После продвижения поле ничем не отличается от обычной колонки, получая все преимущества колоночного хранения.
2. **Компактное хранение редких полей.** Вспомогательные таблицы содержат только фактически заполненные строки; NULL-значения не расходуют место.
3. **Автоматическая эволюция схемы.** Не требуется ручного переопределения структуры при появлении новых полей.
4. **Отсутствие специальных структур данных.** Вспомогательная таблица — это обычная колоночная таблица, все оптимизации к ней применимы автоматически.
5. **Отсутствие переписывания основной таблицы** при добавлении нового поля (если оно остаётся разреженным). Контрастирует с наивным добавлением колонки, требующим инициализации N пустых значений.
6. **Стабильная семантика `_id`.** Внешние индексы и ссылки на строки устойчивы к внутренним операциям движка хранения.

**Недостатки и компромиссы:**

1. **Чтение разреженного поля дороже чтения основной колонки.** LEFT JOIN (в реализации — JOIN через словарь `_id → row_position`) вносит накладные расходы порядка O(n_i) операций хэширования на запрос.
2. **Продвижение — блокирующая операция.** В течение времени продвижения последующие INSERT в продвигаемое поле приостанавливаются. Для больших таблиц (N > 100 млн строк) это может быть заметным временем.
3. **Выбор порога — чувствительный параметр.** Неправильный $\theta$ приводит либо к раздуванию основной таблицы (слишком малый порог), либо к неприемлемой стоимости запросов по редким полям (слишком большой порог).
4. **Отсутствие обратного перехода.** Поле, однажды продвинутое по всплеску активности, остаётся в основной таблице навсегда.
5. **Число вспомогательных таблиц может расти значительно.** При 10 000 уникальных путей до достижения порогов возникнет 10 000 физических таблиц в каталоге. Каждая таблица потребляет некоторый объём памяти на метаданные. В практических сценариях (стандартные логи событий) это, впрочем, не вызывает проблем: число действительно разных путей, как правило, ограничено сотнями.

## 3.7. Алгоритмическая модель INSERT

Для формализации опишем INSERT в таблицу с вычисляемой схемой в виде псевдокода.

```
INPUT: row-chunk C с колонками c_1, ..., c_m (каждая имеет имя field_j и тип t_j)
       текущая схема S (мэппинг field_name -> [types, status, non_null_count, phys_name])

1. start_id = текущее число строк основной таблицы T
2. Добавить к C колонку _id со значениями [start_id, start_id+1, ..., start_id+|C|-1]

3. main_chunk = [_id]         // колонки, идущие в основную таблицу
   sparse_chunks = {}         // map: phys_name -> (id, value) пары

4. Для каждой колонки c_j из C:
     S.append(field_j, t_j)    // регистрирует (field, type), если ещё не было
     phys = storage_column_name(field_j, t_j)

     если S.status(phys) == pinned или status(phys) == promoted:
         append c_j to main_chunk
     иначе (sparse):
         для каждой строки i ∈ [0, |C|):
             если c_j[i] != NULL:
                 sparse_chunks[phys].push_back((start_id+i, c_j[i]))
         S.increment_non_null(phys, число_заполненных)
         если S.non_null_count(phys) >= θ:
             // продвижение
             добавить phys как физическую колонку к T (O(N))
             мигрировать все накопленные (id, value) из sparse-таблицы phys в T
             удалить sparse-таблицу phys

5. Выполнить INSERT в основную таблицу T с main_chunk.
6. Для каждой sparse_chunk: выполнить INSERT в соответствующую вспомогательную таблицу.
```

Параллельность этого алгоритма обсуждается в главе 4. Алгоритмическая модель SELECT аналогична и сводится к скану основной таблицы с последующим присоединением вспомогательных таблиц по `_id` для каждого упомянутого в запросе sparse-поля.

## 3.8. Заключение главы

Предложенная модель хранения сочетает сильные стороны колоночного представления (для часто используемых полей) и разреженного EAV (для редких полей), обходя ключевые ограничения каждого из подходов. Центральные архитектурные решения — хранение разреженных полей в отдельных двухколоночных таблицах, связанных через стабильный логический идентификатор `_id`, а также автоматическое продвижение полей между режимами при пересечении заранее зафиксированного порога плотности — позволяют достичь приемлемого баланса между стоимостью хранения, стоимостью чтения и сложностью реализации.
