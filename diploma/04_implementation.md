# Глава 4. Реализация

Настоящая глава описывает реализацию предложенной в главе 3 схемы хранения в кодовой базе Otterbrix. Основная цель раздела — показать, как архитектурные решения, сформулированные в предыдущей главе, отображаются на конкретные компоненты кода, и какие структурные изменения потребовалось внести в различные подсистемы.

Имена файлов и классов приводятся в соответствии с актуальным состоянием ветки разработки.

## 4.1. Обзор затронутых компонентов

Реализация задействует следующие ключевые подсистемы Otterbrix:

- **`components/catalog/`** — метаданные таблиц. Введён новый класс `computed_schema`, отвечающий за динамическую схему и статус разреженных колонок.
- **`services/dispatcher/`** — центральная точка маршрутизации запросов. Расширен INSERT- и SELECT-путями для таблиц с вычисляемой схемой.
- **`services/disk/`** — менеджер дискового хранилища. Добавлена поддержка создания, удаления и миграции вспомогательных таблиц.
- **`components/sql/transformer/`** — SQL-трансформер. Добавлена поддержка синтаксиса `CREATE TABLE db.t ();` (пустой список колонок) и синтаксиса `INSERT ... VALUES (json('...'))` для вставки JSON-документов.
- **`components/logical_plan/`** — узлы логического плана. Расширены `node_create_collection_t` параметрами `sparse_threshold` и `pinned_columns`.
- **`components/table/`** — низкоуровневое колоночное хранилище. Потребовалось минимальное расширение: поддержка операции `add_column` c генерацией значений по умолчанию.
- **`components/vector/`** — операции над векторами значений. Добавлены placeholder-векторы для поддержки разреженных data_chunk (эта функциональность используется также для проекции колонок, см. главу 5).

## 4.2. Класс `computed_schema`: хранение и эволюция метаданных

Класс `computed_schema` (`components/catalog/computed_schema.hpp/.cpp`) инкапсулирует весь учёт метаданных таблицы с вычисляемой схемой. Его публичный интерфейс и ключевые поля устроены следующим образом.

### 4.2.1. Поля состояния

```cpp
// field_name -> list of types currently present (один field может
// иметь несколько типов, если разные INSERT-ы вставляли разные типы)
std::pmr::unordered_map<std::pmr::string,
                        std::pmr::vector<types::complex_logical_type>> fields_;

// Порядок появления (field, type) пар — соответствует
// порядку физических колонок в основной таблице
std::pmr::vector<std::pair<std::pmr::string,
                           types::complex_logical_type>> column_order_;

// sparse_threshold, заданный при CREATE TABLE (0 = нет разреженного режима)
uint64_t sparse_threshold_{0};

// Счётчик ненулевых значений по каждому физическому имени (phys_name)
std::pmr::unordered_map<std::pmr::string, uint64_t> non_null_counts_;

// Флаг «всё ещё разреженное» по каждому phys_name
std::pmr::unordered_map<std::pmr::string, bool> sparse_flags_;

// Порядок продвижения из sparse → promoted
std::pmr::vector<std::pair<std::pmr::string,
                           types::complex_logical_type>> promoted_order_;

// phys_name -> (field_name, type): обратная карта
std::pmr::unordered_map<std::pmr::string,
    std::pair<std::pmr::string,
              types::complex_logical_type>> phys_to_field_type_;

// Pinned-колонки, заданные при CREATE TABLE
std::unordered_set<std::string> pinned_field_names_;

// Колонки, впервые попавшие в схему как pinned и ожидающие
// физической материализации
std::vector<sparse_column_info> newly_pinned_;
```

Центральное понятие — **физическое имя колонки** (phys_name), формируемое по правилу:

```
phys_name = "__" + field_name + "__" + std::to_string(type_enum_value)
```

Два префикса подчёркивания зарезервированы для служебных колонок и гарантируют, что автоматически порождённые имена не конфликтуют с именами, которые пользователь может ввести явно. Число (тип) в суффиксе необходимо потому, что одна и та же логическая колонка может существовать в нескольких типах: например, если первый INSERT вставил `{"price": 100}`, а следующий `{"price": "free"}`, в схеме появляются две отдельные физические колонки `__price__INT64` и `__price__STRING`. Каждая из них независимо подсчитывает свою плотность и может продвигаться независимо.

### 4.2.2. Центральные операции

**`append(field_name, type)`** — регистрирует новую пару (field, type) в схеме, если её ещё нет. Также определяет начальный статус колонки:

- Если `field_name` ∈ `pinned_field_names_`, колонка сразу получает статус promoted и добавляется в `newly_pinned_` (диспетчер затем вызовет `storage_add_column` для материализации).
- В остальных случаях, если `sparse_threshold_ > 0`, колонка получает статус sparse.
- Если порог равен нулю, колонка сразу становится promoted (разреженное хранение отключено).

**`increment_non_null(phys_name, count)`** — увеличивает счётчик ненулевых значений. Возвращает `true`, если после инкремента колонка пересекла порог и должна быть продвинута. Метод также атомарно обновляет `sparse_flags_` и добавляет продвинутую колонку в `promoted_order_`.

**`latest_types_struct()`** — возвращает полную актуальную схему таблицы в виде структурного типа, в виде, пригодном для инициализации `data_chunk_t`. Важно, что эта схема:

- Предпосылает служебную колонку `_id BIGINT` (если `sparse_threshold_ > 0`).
- Исключает колонки, всё ещё находящиеся в разреженном состоянии — они не являются физическими колонками основной таблицы.
- Сохраняет порядок, соответствующий физическому расположению в основной таблице.

**`sparse_table_name(collection, field_name, type)`** — генерирует имя вспомогательной таблицы по паттерну `<collection>__sp__<field>__<type>`. Пример: для основной таблицы `mydb.events` и поля `commit.rev` типа STRING имя вспомогательной таблицы — `mydb.events__sp__commit.rev__STRING_LITERAL`.

### 4.2.3. Потокобезопасность

Текущая реализация `computed_schema` синхронизируется внешним блокирующим мьютексом на уровне каталога (`catalog_mutex_` в `catalog::catalog`). Каждое изменение схемы — регистрация нового поля, увеличение счётчика, продвижение — выполняется под эксклюзивной блокировкой.

Компромисс здесь сделан сознательно: параллельность INSERT в разные таблицы полностью независима (каждая таблица имеет собственный каталожный объект), а INSERT-ы в одну и ту же таблицу сериализуются на уровне диспетчера всё равно — вследствие необходимости атомарного получения `start_id`. Введение более мелкозернистых блокировок на уровне `computed_schema` не дало бы заметного выигрыша.

## 4.3. Диспетчер: маршрутизация INSERT

Основной путь INSERT для таблиц с вычисляемой схемой реализован в `services/dispatcher/dispatcher.cpp`. Ветвление происходит в обработчике узла логического плана `insert_t`: если каталог сообщает `catalog_.table_computes(id)`, выбирается специализированный путь вычисляемой схемы, а не общий путь фиксированной схемы.

### 4.3.1. Разреженный путь

Алгоритмически путь повторяет псевдокод из раздела 3.7. Конкретные шаги реализации:

**Шаг 1. Получение start_id.** Отправляется асинхронное сообщение `manager_disk_t::storage_total_rows` дисковому менеджеру. Оператор `co_await` приостанавливает выполнение до получения ответа. Полученное значение сохраняется как `start_id`.

**Шаг 2. Итерация по колонкам входного чанка.** Для каждой колонки `col` вычисляется `field_name = col.type().alias()` (имя колонки хранится как alias типа — удобная эксплуатация системы типов Otterbrix), затем `phys_name` через `storage_column_name()`. Вызов `schema.append(...)` регистрирует колонку.

**Шаг 3. Классификация.** Проверка `schema.is_sparse(phys_name)`:

- Если колонка sparse: выполняется цикл по строкам, в котором для каждой ненулевой строки формируется пара `(start_id + row_idx, value)`. Пары накапливаются в структуру `sparse_entry_t`, содержащую field_name, тип, phys_name и список пар.
- Если колонка не sparse: колонка добавляется в вектор `promoted_cols`, который позже формирует чанк для основного INSERT.

После цикла `schema.increment_non_null(phys_name, non_null_count)` вызывается для детекции продвижения текущим батчем; если продвижение произошло, информация о колонке помещается в вектор `just_promoted`.

**Шаг 4. Обработка первых вставок pinned-колонок.** Вызов `schema.take_newly_pinned()` возвращает список pinned-колонок, которые были впервые зарегистрированы в этой операции INSERT. Для каждой из них отправляется асинхронный запрос `manager_disk_t::storage_add_column`. Это единственное место, где физическая колонка создаётся **до** основного INSERT (а не после): pinned-колонка обязана существовать в схеме основной таблицы до того, как в неё попадут данные.

**Шаг 5. Формирование чанка для основного INSERT.** Оригинальный `chunk.data` очищается и заполняется заново:
1. Добавляется колонка `_id` с последовательностью `[start_id, start_id+1, ..., start_id+N-1]`. Конструкция `id_vec.sequence(start_id, 1, row_count)` заполняет буфер за один проход.
2. Добавляются все элементы `promoted_cols` в порядке их сбора.

**Шаг 6. Создание физических колонок для just_promoted.** Для каждой из колонок, продвинутых в этом батче, отправляется `storage_add_column`. Это делается **после** предыдущего шага, так как данные продвинутой колонки ещё лежат во вспомогательной таблице — миграция произойдёт позже.

**Шаг 7. Основной INSERT.** Вызывается `execute_plan_impl` с обновлённым чанком, который уходит в обычный путь записи в основную таблицу.

**Шаг 8. Запись в разреженные таблицы.** Для каждой `sparse_entry` из шага 3:
1. Через `storage_create` при необходимости создаётся вспомогательная таблица (операция идемпотентна).
2. Строится двухколоночный чанк `(_id, value)` из накопленных пар.
3. Вызывается `storage_append` для записи в вспомогательную таблицу.

**Шаг 9. Миграция just_promoted.** Для каждой продвинутой колонки:
1. Полное сканирование основной таблицы с извлечением пар `(_id, row_position)` — строится словарь для патчинга.
2. Полное сканирование вспомогательной таблицы: для каждой её строки находится `row_position` в основной, и значение записывается в соответствующую ячейку через `storage_patch_column`.
3. Вспомогательная таблица удаляется.

### 4.3.2. Неразреженный путь

При `sparse_threshold == 0` вычисляемая схема не использует разреженное хранение. Путь существенно проще: для каждой колонки входного чанка выполняется `schema.append`, при отсутствии колонки в физической схеме — `storage_add_column`, затем стандартный INSERT.

Этот путь был реализован первым и лёг в основу концепции; разреженный путь был введён как расширение.

## 4.4. Диспетчер: маршрутизация SELECT

SELECT-путь для таблицы с разреженными колонками реализован как пост-обработка результата основного запроса. Логика следующая:

1. Основной запрос (`SELECT ... FROM t`) исполняется стандартным образом над основной таблицей. Результат — обычный `data_chunk_t` с колонками основной таблицы, включая служебную `_id`.

2. Если в SQL-запросе упоминаются поля, которые на момент выполнения являются разреженными, диспетчер добавляет к результату дополнительные колонки, выполняя следующую последовательность:

   a) Поиск колонки `_id` в результирующем чанке — её позиция используется как ключ связи.
   
   b) Построение словаря `_id → позиция строки в результате`. Для чанка размера $n$ это требует O(n) времени и памяти.
   
   c) Для каждой запрошенной разреженной колонки:
      - Полное сканирование соответствующей вспомогательной таблицы.
      - Создание нового `vector_t` с типом колонки и маской валидности, изначально установленной во все-NULL.
      - Итерация по строкам вспомогательной таблицы: извлечение `_id`, поиск в словаре, при совпадении — запись значения в новый вектор по найденной позиции.
      - Добавление получившегося вектора к результирующему чанку.

3. Служебная колонка `_id` в итоговом результате опционально убирается, если пользователь не запрашивал её явно (в текущей реализации она сохраняется, так как это удобно для дальнейших запросов; окончательное решение этого вопроса оставлено для будущих версий).

Такая реализация функционально эквивалентна LEFT JOIN основной и вспомогательных таблиц, но избегает создания полноценного плана JOIN. Это упрощает кодовую базу на текущем этапе, однако оставляет открытым вопрос о применимости оптимизаций JOIN (например, push-down предикатов через JOIN). Перевод SELECT-пути на явные узлы LEFT JOIN в логическом плане обсуждается в главе 6 как направление будущей работы.

## 4.5. SQL-трансформер: поддержка новых конструкций

### 4.5.1. `CREATE TABLE db.t ();`

Для создания таблицы с вычисляемой схемой используется синтаксис с пустым списком колонок. SQL-трансформер (`components/sql/transformer/impl/transform_table.cpp`) распознаёт `CreateStmt` с пустым `tableElts` и создаёт `node_create_collection_t` с флагом `has_dynamic_schema=true`.

Параметры разреженного хранения передаются через опциональный синтаксис WITH:

```sql
CREATE TABLE db.t () WITH (sparse_threshold = 10000);
CREATE TABLE db.t () WITH (sparse_threshold = 10000,
                            pinned_columns = 'commit.rev,commit.operation');
```

Парсинг опций реализован в виде отдельной процедуры разбора, возвращающей структуру, из которой затем инициализируется `node_create_collection_t`.

### 4.5.2. `INSERT INTO db.t VALUES (json('...'))`

Этот синтаксис предоставляет удобный способ вставки JSON-документов напрямую из SQL, без предварительного разбора схемы на стороне клиента. SQL-трансформер детектирует конструкцию `json('...')` как вызов функции (FuncCall) с одним строковым аргументом в контексте VALUES-строки без указания списка колонок INSERT.

При обнаружении такой конструкции активируется специальный путь `build_json_insert`:

1. Каждая VALUES-строка разбирается как JSON-документ через библиотеку Boost.JSON.
2. JSON рекурсивно «расплющивается»: вложенные объекты порождают пути с точечной нотацией (`user.profile.age`), массивы сериализуются обратно в JSON-строки, null-значения пропускаются.
3. По всему батчу строится объединение путей. Для каждого пути определяется тип на основании первого ненулевого значения.
4. Создаётся `data_chunk_t` с колонками по числу уникальных путей, инициализированный всеми-NULL; для каждой строки проставляются значения найденных в ней полей.
5. Формируется `node_insert_t`, который далее идёт в диспетчер и попадает в стандартный путь INSERT для вычисляемой схемы.

Имена колонок результирующего чанка сохраняют точечную нотацию. На стороне `computed_schema` эти имена проходят через `storage_column_name` и становятся физическими именами колонок, соблюдая принцип локальности: колонка `user.profile.age` получит уникальное физическое имя `__user.profile.age__<type>`.

## 4.6. Модификации подсистемы дискового хранилища

Ключевое изменение в `services/disk/manager_disk.hpp` — введение двух новых операций:

- **`storage_create_table`** (была ранее; расширена поддержкой динамической схемы).
- **`storage_add_column(collection_name, column_definition)`** — добавление колонки в существующую таблицу. Реализация делегируется `data_table_t::add_column`, которая создаёт новый объект таблицы, в котором:
  - Сохраняются ссылки на существующие колоночные буферы (shared_ptr-семантика).
  - Выделяется новый буфер для добавляемой колонки с ёмкостью, равной текущему числу строк.
  - Буфер заполняется значениями по умолчанию (NULL или явно указанным defaults).

Важный аспект: старые колонки **не копируются**; новый `data_table_t` просто разделяет их с родительским. Единственная O(N) работа — это инициализация буфера новой колонки. Эта характеристика была проанализирована отдельно в рамках работы (раздел «Схема эволюция» главы 3) и послужила обоснованием решения не переносить редкие колонки в основную таблицу по умолчанию.

## 4.7. Параллельность и корректность

Работа с разреженными таблицами в Otterbrix корректно встраивается в существующую акторную модель параллельного исполнения:

- **Параллельность между таблицами.** INSERT-ы и SELECT-ы в разные коллекции обрабатываются независимыми акторами и не создают взаимных блокировок.
- **Параллельность между INSERT и SELECT в одной таблице.** Действующий MVCC-протокол основной таблицы распространяется и на вспомогательные: SELECT видит снимок состояния на момент начала транзакции, в том числе для разреженных колонок, так как все записи во вспомогательные таблицы выполняются в рамках той же транзакции, что и основной INSERT.
- **Сериализация INSERT в одну таблицу.** INSERT-ы в одну и ту же таблицу сериализуются на уровне получения `start_id`: два параллельных INSERT запрашивают `start_id` у актёра дискового менеджера, и этот актёр обеспечивает атомарное выделение непересекающихся диапазонов идентификаторов. Дальнейшая обработка (запись в основную таблицу, запись в разреженные таблицы) может идти параллельно.
- **Атомарность продвижения.** Продвижение (миграция данных из разреженной таблицы в основную) выполняется в рамках одной транзакции. Если продвижение обнаруживает конфликт (например, параллельная сессия уже продвинула ту же колонку), операция корректно отменяется и повторяется.

Совокупно система обеспечивает согласованность в духе snapshot isolation: каждая транзакция видит консистентное состояние таблицы, включая разреженные колонки, независимо от параллельных операций.

## 4.8. Тестовое покрытие

Для реализации разработано обширное тестовое покрытие, включающее:

- **Модульные тесты** (`components/catalog/tests/`, `components/sql/test/`) — проверка корректности `computed_schema` в изоляции: регистрация полей, детекция продвижения, корректность pinned-колонок; распознавание SQL-конструкций `CREATE TABLE db.t ()` и `INSERT ... VALUES (json(...))`.
- **Интеграционные тесты** (`integration/cpp/test/test_computed_schema.cpp`) — более 30 сценариев, включая:
  - Базовый INSERT и SELECT с автоматической эволюцией схемы.
  - Эволюция между батчами: добавление нового поля, появление нового типа для существующего поля.
  - Разреженное хранение: вставка редких полей, проверка, что они не попадают в основную таблицу.
  - Продвижение: постепенное насыщение редкого поля до достижения порога, проверка миграции данных.
  - Pinned-колонки: их немедленная материализация даже при отсутствии данных.
  - Запросы, смешивающие плотные и разреженные поля: корректность LEFT JOIN-реконструкции.
  - Граничные случаи: пустой INSERT, INSERT одного поля с NULL, одновременный INSERT разных типов для одного поля.
- **Тесты производительности** (`JSONBench/otterbrix/jsonbench.cpp`) — сравнение с ClickHouse и PostgreSQL на стандартном датасете Bluesky JSONBench (см. главу 6).

Полный прогон всех тестов в конфигурации Debug занимает около 50 секунд и насчитывает свыше 470 тестовых сценариев. Все тесты на момент завершения работы проходят успешно.

## 4.9. Итоги главы

Реализация предложенной в главе 3 архитектуры потребовала:

1. Введения нового класса метаданных `computed_schema`, инкапсулирующего учёт динамической схемы и разреженного статуса колонок.
2. Расширения пути обработки INSERT в диспетчере сложной последовательностью действий, включающей классификацию колонок, параллельную запись в основную и вспомогательные таблицы, миграцию продвинутых колонок.
3. Расширения пути обработки SELECT пост-обработчиком, реконструирующим разреженные колонки через lookup по `_id`.
4. Расширения SQL-трансформера поддержкой динамического `CREATE TABLE` и `INSERT ... VALUES (json(...))`.
5. Минимальных правок низкоуровневых подсистем хранения — поддержки `storage_add_column` и базовых операций над малыми двухколоночными таблицами.

Интеграция с существующей акторной моделью параллелизма не потребовала введения новых механизмов синхронизации; взаимная непротиворечивость операций обеспечивается за счёт повторного использования MVCC-протокола, действующего для обычных таблиц.

Следующая глава описывает оптимизации физических операторов, существенно повысившие производительность итоговой системы.
