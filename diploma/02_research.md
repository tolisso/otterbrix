# Глава 2. Исследование существующих подходов к хранению JSON в СУБД

## 2.1. Постановка вопроса

Прежде чем предлагать собственное решение, необходимо зафиксировать, какие именно подходы к хранению полуструктурированных данных применяются в современных СУБД, каковы их сильные и слабые стороны, какие из них теоретически обоснованы в академической литературе, и какой из них наилучшим образом подходит для колоночного движка с расширяемой схемой.

В настоящей главе рассматриваются четыре принципиально различных подхода:

1. Хранение JSON как неделимого значения (в том числе в бинарном формате BSON/JSONB).
2. Модель Entity-Attribute-Value (EAV) и её вариации (нормализованное реляционное представление иерархических данных через родительский идентификатор или через разворот путей).
3. Колонка на каждый путь JSON (схема, развёрнутая заранее или разворачиваемая автоматически при вставке).
4. Новый тип данных JSON в ClickHouse, сочетающий колонки для часто встречающихся путей с внутренним форматом для редких.

Каждый из подходов анализируется с точки зрения трёх характеристик, критичных для аналитических нагрузок на полуструктурированных данных:

- **Эффективность ввода-вывода** при запросе к отдельному полю: сколько байт с диска нужно прочитать, чтобы получить одно поле для одной строки.
- **Локальность кэша** при обработке большого числа строк: насколько близко друг к другу в памяти располагаются значения одного поля из разных строк.
- **Стоимость эволюции схемы**: что происходит при появлении нового поля в данных, и как это отражается на уже хранимых строках.

## 2.2. Хранение JSON как неделимого значения

Исторически первый и до сих пор наиболее распространённый способ хранения JSON-документов в реляционных СУБД — рассматривать документ целиком как значение одной ячейки особого типа JSON. Документ сериализуется в строковом виде (текстовый JSON) или в бинарном (BSON, MessagePack, JSONB в PostgreSQL).

**Текстовый JSON.** MySQL до версии 5.7 и Oracle Database хранили JSON как тип CLOB — произвольную строку без внутреннего индексирования. При каждом обращении к полю происходил полный разбор строки парсером. Этот подход обеспечивает простоту реализации, совместимость с внешними инструментами и полное воспроизведение исходной структуры, но делает выборочный доступ к отдельному полю дорогой операцией: для извлечения скалярного значения приходится повторно парсить весь документ.

**Бинарный JSON: BSON и JSONB.** MongoDB (BSON), PostgreSQL (JSONB, начиная с версии 9.4) и MySQL 5.7+ перешли на бинарное представление, в котором:

- документ предварён таблицей смещений внутренних элементов;
- каждое скалярное значение хранится в нативном бинарном формате (например, int64 без преобразования в строку);
- ключи объектов упорядочены для ускорения бинарного поиска.

Этот подход позволяет обращаться к отдельному полю за время O(log n) по количеству ключей документа, без полного разбора. Однако два фундаментальных недостатка сохраняются:

1. **Полное чтение документа с диска.** Страница диска в СУБД типично составляет 4–16 КБ, а один документ JSONB нередко имеет размер от единиц до десятков килобайт. Для запроса `SELECT doc->'user'->'id' FROM t WHERE doc->'kind' = 'commit'` система должна считать с диска каждый документ целиком, хотя фактически в каждом документе требуются два поля суммарным размером порядка нескольких десятков байт.
2. **Отсутствие колоночного доступа.** Несколько последовательных строк таблицы содержат свои документы, разнесённые по страницам; чтение одного и того же поля для миллиона строк приводит к миллиону разрозненных обращений к памяти (cache misses). Современные процессоры при такой схеме демонстрируют производительность на порядок ниже пиковой.

Эмпирически на бенчмарке JSONBench PostgreSQL с JSONB и сравнительно простыми аналитическими запросами демонстрирует производительность в 10–30 раз ниже колоночных СУБД на том же объёме данных.

Существуют попытки частично смягчить указанные проблемы за счёт функциональных (expression) индексов: `CREATE INDEX ON t ((doc->'kind'))`. Такие индексы ускоряют выборку по конкретному пути, но не решают фундаментальной проблемы ввода-вывода при последующем чтении других полей и не ускоряют агрегатные запросы, затрагивающие всю таблицу.

## 2.3. Модель Entity-Attribute-Value (EAV)

EAV — классическая реляционная техника моделирования данных с переменной структурой, описанная в литературе ещё в 1970–1980-е годы в контексте медицинских и биологических баз данных (Stead et al., 1983 [2]). Идея состоит в декомпозиции гетерогенных записей в универсальную тройку:

```
CREATE TABLE attr (
  entity_id BIGINT,
  attr_name TEXT,
  attr_value TEXT
);
```

Документ `{"a": 1, "b": "x"}` превращается в две строки: `(1, 'a', '1')` и `(1, 'b', 'x')`. Запрос `SELECT a FROM t` принимает вид `SELECT attr_value FROM attr WHERE attr_name = 'a'`.

**Сильные стороны:**

- Схема полностью динамическая: добавление нового поля не требует ALTER TABLE — просто появляются новые строки с новым `attr_name`.
- Отсутствие NULL-значений: строки существуют только для фактически заполненных полей.
- Простая модель мутаций: обновление поля — это UPDATE одной строки в `attr`.

**Слабые стороны, многократно описанные в литературе** (Nadkarni et al., 2007 [3]; Dinu and Nadkarni, 2007 [4]):

- **Потеря типизации.** Все значения приводятся к строке (либо вводится отдельная колонка на каждый физический тип, что частично размывает идею). Агрегация числовых полей требует преобразования типов на каждой строке.
- **Деградация запросов с несколькими полями.** Запрос `SELECT a, b, c FROM t` становится трёхкратным self-join (`attr a JOIN attr b ON a.entity_id = b.entity_id JOIN ...`) либо группировкой с условными агрегатами. В любом случае сложность превышает колоночный вариант на порядок.
- **Иерархия.** Для вложенных JSON-документов `{"a": {"b": {"c": 1}}}` возникает выбор между двумя не-эквивалентными решениями, каждое со своими ограничениями:
  - **Через `parent_id`.** Вводится колонка `parent_id`, и узлы дерева связываются рекурсивно. Доступ к листу `a.b.c` требует рекурсивного обхода (в SQL — рекурсивных CTE). Этот вариант теоретически универсален, но практически непригоден для аналитики.
  - **Через разворот путей (flattened paths).** Каждый лист документа представляется одной строкой вида `(entity_id, 'a.b.c', 1)`. Отсутствует рекурсия, но теряется различие между структурными и листовыми узлами (объекты-пустышки невозможно отличить от отсутствующих). Вариант описан в работах по обработке XML и JSON в реляционных СУБД (Beyer et al., 2006 [5]; Florescu and Kossmann, 1999 [6]).

Обе вариации EAV страдают от общего недостатка: **колоночный доступ к одному полю невозможен без предикатного сканирования по `attr_name`**. Как следствие, аналитические нагрузки деградируют многократно.

Академическая литература формулирует это явление в терминах «vertical fragmentation» (Copeland and Khoshafian, 1985 [7]): декомпозиция сущности на отдельные строки теоретически выигрывает место, но принципиально лишается возможности оптимизировать групповой доступ к полям.

## 2.4. Колонка на каждый путь JSON

Альтернативный подход, к которому пришли современные аналитические движки (Snowflake VARIANT, ClickHouse JSON в ранних версиях, ряд коммерческих систем) — **разворачивать JSON-документ в колоночное представление**, где каждый уникальный путь становится отдельной физической колонкой.

Документ `{"a": 1, "b": "x", "c": {"d": 2}}` при вставке порождает три колонки: `a` (INT), `b` (STRING), `c.d` (INT). Отсутствующие в конкретном документе поля записываются как NULL.

**Сильные стороны:**

- Колоночный доступ в полной мере: для запроса по одному полю читается ровно одна колонка, без лишнего ввода-вывода.
- Полная типизация: каждое поле имеет собственный тип и может использовать стандартные оптимизации (сжатие, zone maps, поколоночные индексы).
- Vectorized execution: операторы обрабатывают значения поля пакетами, эффективно используя кэш и SIMD.

**Слабые стороны:**

- **Рост числа физических колонок.** Реальные полуструктурированные данные содержат длинный хвост редких полей. В наборе JSONBench из публичного потока сети Bluesky (около 40 миллионов событий) при полной развёртке обнаруживается более 10 тысяч уникальных JSON-путей, при этом 99% событий используют лишь около 50 путей. Классическая СУБД с дисковыми страницами фиксированного размера не справляется с таблицей в 10 000 колонок.
- **Разрастание NULL-значений.** Для каждой новой редкой колонки все N ранее вставленных строк получают NULL. При N = 10 млн строк и, скажем, 5 000 редких колонок только на битмаски валидности требуется порядка 6 ГБ (10 млн × 5 000 бит). Если значения хранятся в явном виде с резервированием места под тип, расход памяти становится неприемлемым.
- **Стоимость ALTER TABLE ADD COLUMN.** Каждый вызов добавления колонки требует O(N) работы по инициализации N значений по умолчанию для всей истории таблицы. На больших таблицах это делает операцию практически неисполнимой в онлайн-режиме.

Теоретические основы колоночного хранения описаны в работах C-Store (Stonebraker et al., 2005 [8]), MonetDB/X100 (Boncz et al., 2005 [9]), Vectorwise (Zukowski and Boncz, 2012 [10]). Во всех этих работах рассматривается случай фиксированной известной заранее схемы; случай динамической схемы с произвольным ростом числа колонок не был предметом систематического анализа до недавнего времени.

## 2.5. Механизм JSON в ClickHouse

Наиболее продвинутым промышленным решением в области колоночного хранения полуструктурированных данных на сегодня является новый тип данных `JSON` в ClickHouse, введённый в версии 24.8 (в экспериментальном статусе) и стабилизированный в 24.10. Схема хранения устроена следующим образом (Kostenko, 2024 [11]):

**Частично развёрнутая схема.** Тип декларируется как
```
JSON(
  max_dynamic_paths = N,
  field_1 Type_1,
  field_2 Type_2,
  ...
)
```
Часть путей объявляется явно (с зафиксированным типом), и они становятся полноценными колонками основной таблицы со всеми свойствами колоночного хранения (сжатие, zone maps, специализированные кодеки). Остальные пути помещаются в общее хранилище `shared data`.

**Shared data.** Редкие пути хранятся внутри строки таблицы как пара вложенных массивов: `{"paths": [path_1, path_2, ...], "values": [value_1, value_2, ...]}`. По сути, это EAV-представление, упакованное внутрь одной ячейки. Для операций чтения ClickHouse выполняет лениво разбор массива при обращении к конкретному пути через функции `JSONExtract`.

**Динамическое продвижение.** При вставке новых данных система отслеживает частоту появления путей. Пути, частота которых превышает заданный порог `max_dynamic_paths` (по умолчанию 1024), автоматически «продвигаются» в полноценные колонки на следующем слиянии (merge). Этот процесс происходит в фоне и невидим для пользователя.

**Сильные стороны подхода ClickHouse:**

- Автоматическое распознавание часто встречающихся путей без вмешательства разработчика.
- Эффективный колоночный доступ к «популярным» полям.
- Компактное хранение длинного хвоста редких полей.

**Ограничения:**

- **Ограниченный набор операций над `shared data`.** Агрегации по путям из shared data существенно медленнее, чем по полноценным колонкам. Индексы (primary key, skip indices) не применяются к редким путям.
- **Отсутствие кросс-документной колоночной локальности для shared data.** Чтобы узнать значение редкого поля в 100 строках, ClickHouse должен разобрать 100 массивов, каждый из которых содержит несколько десятков путей.
- **Стоимость слияний.** Перенос пути из shared data в отдельную колонку требует переписывания всех кусков хранения (parts), затронутых полем. Операция выполняется фоновыми процессами merge, но временно удваивает потребление диска.

Важно: в текущей реализации ClickHouse редкие пути хранятся внутри каждой строки, что означает дублирование ключей пути в каждой строке. Если путь `commit.record.author.did` встречается в миллионе строк, строка `"commit.record.author.did"` будет записана миллион раз (с применением словарной компрессии, но всё же в логически миллионной кратности).

## 2.6. Предварительные выводы

Проведённый анализ позволяет сформулировать требования к разрабатываемому решению:

1. **Часто встречающиеся поля должны храниться как полноценные колонки** — это необходимое условие для достижения производительности, сопоставимой с ClickHouse, на типичных аналитических запросах.
2. **Редко встречающиеся поля должны храниться отдельно от основной таблицы** — прямолинейное раздувание схемы неприемлемо; размещение редких значений внутри каждой строки (как в ClickHouse shared data) сохраняет проблему чтения лишних данных при колоночных запросах.
3. **Должна существовать процедура автоматической миграции полей между режимами** по мере роста их частоты, без необходимости ручного вмешательства в схему.
4. **Для разреженных полей нужно сохранить возможность применения стандартных операций** (предикаты, индексы, агрегации) — желательно без специализированного кода, за счёт переиспользования существующих механизмов реляционного движка.

Совокупно эти требования приводят к решению, описанному в следующей главе: хранение каждого разреженного пути в отдельной вспомогательной таблице формата `(_id, value)` с организацией чтения через LEFT JOIN, с автоматическим продвижением пути в основную таблицу при достижении порога заполненности. Такое решение комбинирует сильные стороны колоночного подхода и EAV, обходя ключевые ограничения каждого из них.
