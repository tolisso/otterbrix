# Глава 1. Постановка задачи и исходная архитектура Otterbrix

## 1.1. Общая характеристика проекта Otterbrix

Otterbrix — это встраиваемый вычислительный фреймворк с открытым исходным кодом, предназначенный для обработки полуструктурированных данных (JSON-подобных документов) в сочетании с классической реляционной моделью. Проект развивается как альтернатива специализированным документным СУБД (MongoDB, Couchbase) и аналитическим колоночным СУБД (ClickHouse, DuckDB), предлагая унифицированную модель, в которой SQL-запросы могут одновременно обращаться к структурированным таблицам и к полям JSON-документов в рамках одного исполнителя.

Архитектурно Otterbrix построен на ряде хорошо известных принципов современных СУБД:

- **Акторная модель параллелизма** (реализована поверх библиотеки actor-zeta) — все ключевые компоненты (дисковый менеджер, WAL, диспетчер, менеджер индексов) оформлены как независимые актёры, обменивающиеся сообщениями. Это даёт предсказуемую изоляцию состояния и позволяет масштабировать систему на большое число ядер без глобальных блокировок.
- **Корутины C++20** (co_await / co_return) — используются для организации асинхронного исполнения планов запросов. Каждый план запроса может приостанавливаться на ожидании диска, других актёров или внешних событий, не блокируя нить пула.
- **Полиморфные аллокаторы (`std::pmr`)** — вся работа с памятью идёт через конкретный `memory_resource`, что позволяет локализовать аллокации запросов, контролировать фрагментацию и обеспечивать точный учёт потребления памяти.
- **Собственный SQL-парсер на базе libpg_query** — грамматика PostgreSQL обеспечивает совместимость с широким спектром существующих запросов и инструментов.
- **Колоночное хранилище** — таблицы организованы как последовательность row groups, каждый из которых содержит независимые колоночные сегменты. Это стандартный приём для ускорения аналитических запросов (сканирование, агрегация, фильтрация).

На момент начала работы над выпускной квалификационной работой проект находился в активной фазе рефакторинга: команда завершала переход с гибридной модели хранения (отдельные подсистемы для «документов» и «таблиц») на единое колоночное хранилище. Этот переход, оформленный одним крупным коммитом (`a34d3823`, «Remove components/document and migrate to columnar data_chunk storage», февраль 2026), удалил более 18 000 строк кода и послужил отправной точкой для настоящей работы.

## 1.2. Исторически сложившаяся двойственность: таблицы и документы

До указанного рефакторинга Otterbrix поддерживал два принципиально различных типа коллекций:

1. **Документные коллекции** — использовали отдельный компонент `components/document/`, реализовавший собственный вариант иерархического JSON-подобного значения. Каждый документ представлял собой дерево (объекты, массивы, скалярные листья), сериализованное в формате, близком к BSON. Доступ к полям происходил по JSON-указателю (`/commit/record/text`), каждый документ хранился как неделимое значение.

2. **Табличные коллекции** — использовали колоночное хранилище `components/table/` с фиксированной схемой (набор колонок фиксированных типов). Доступ к ячейкам происходил по паре (row_id, column_id); каждая колонка хранилась в отдельном сегменте памяти/диска.

Обе реализации имели собственную подсистему хранения, собственные операторы исполнения (match, group, sort, insert, update, delete), собственные адаптеры диска, собственный WAL-формат. Класс `document_t` (`components/document/document.hpp`, удалён в `a34d3823`) насчитывал около 1100 строк кода и реализовывал полнофункциональный JSON-документ с поддержкой мутаций через `set(json_pointer, value)`, `remove(json_pointer)`, `set_array`, `set_dict`, а также операций сравнения и сериализации.

Основные недостатки документной реализации, зафиксированные в ходе предварительного анализа:

- **Неэффективный ввод-вывод при аналитических запросах.** Для ответа на запрос вида `SELECT COUNT(*) FROM t WHERE commit.operation = 'create'` система вынуждена была читать с диска полный документ целиком, хотя для ответа требовалось единственное поле. В силу переменной длины документов диск приходилось читать страницами, кэш процессора засорялся неиспользуемыми данными.
- **Низкая локальность кэша L1/L2.** Каждое обращение по JSON-указателю представляло собой обход дерева узлов, расположенных в куче и связанных указателями. В аналитических запросах, обрабатывающих миллионы документов, такой доступ практически полностью исключал полезное попадание в кэш.
- **Невозможность применения векторных оптимизаций.** Векторизованные операторы, повсеместно используемые в современных колоночных СУБД (пакетное сравнение, пакетное вычисление хэшей, SIMD), требуют компактного, однотипного расположения значений в памяти. Документы в формате дерева узлов принципиально не удовлетворяют этому требованию.
- **Удвоенная кодовая база.** Наличие двух параллельных реализаций операторов (документной и табличной) приводило к постоянной рассинхронизации: оптимизации, вводимые в один путь, не переносились в другой; баги всплывали в двух местах независимо; тестовое покрытие росло квадратично.

## 1.3. Миграция на единое колоночное хранилище

Коммит `a34d3823` завершил миграцию: компонент `components/document/` был удалён полностью, все коллекции стали хранить данные в формате `data_chunk_t` — структуры из `components/vector/`, представляющей собой вектор колонок (`std::vector<vector_t> data`) с общим числом строк. Каждая колонка хранится в виде сегментов `vector_t`, поддерживающих несколько представлений данных (flat, constant, dictionary) и плоский массив значений одного типа.

После миграции таблицы получили два подвида:

- **Таблицы с фиксированной схемой**: колонки задаются при `CREATE TABLE db.t (id INT, name TEXT);` и остаются неизменными в течение жизни таблицы. INSERT требует явного перечисления колонок и значений.
- **Таблицы с вычисляемой (computed) схемой**: создаются без предварительного перечисления колонок — `CREATE TABLE db.t ();`. Каждая операция INSERT способна добавить новые поля; схема расширяется по мере поступления данных. Именно этот режим заменил бывшие «документные» коллекции и стал основным предметом настоящей работы.

Миграция закрыла проблему удвоенной кодовой базы, но оставила открытым ключевой вопрос: **как именно хранить колонки, заполненные лишь в небольшой доле строк**. Прямолинейный вариант — создавать физическую колонку на каждый путь JSON и заполнять её NULL для отсутствующих значений — порождает две новые проблемы:

1. **Катастрофический рост пространства.** Реальные полуструктурированные данные (в том числе стандартный датасет JSONBench, сформированный из публичного потока сети Bluesky) содержат десятки тысяч различных JSON-путей, большинство из которых встречаются в менее чем 0.1% документов. При наивном хранении такие таблицы заполняются NULL-значениями на 99% и более.
2. **Замедление записи.** Каждое добавление новой колонки в существующую таблицу требует выделения буфера для всех N ранее вставленных строк и заполнения его значениями по умолчанию. При наивной реализации стоимость ALTER TABLE ADD COLUMN линейна по числу уже хранимых строк.

## 1.4. Формулировка задачи

Цель выпускной квалификационной работы сформулирована следующим образом:

**Спроектировать и реализовать эффективный механизм хранения полуструктурированных данных в рамках колоночного движка Otterbrix, сочетающий производительность колоночного доступа к часто встречающимся полям с компактным представлением редко встречающихся полей, без необходимости поддерживать отдельную подсистему для JSON-документов.**

Для достижения поставленной цели необходимо решить следующие задачи:

1. Проанализировать существующие в индустрии подходы к хранению полуструктурированных данных в СУБД (разделы, посвящённые BSON в PostgreSQL, модели Entity-Attribute-Value, flatten-представлению путей, а также новому механизму типа JSON в ClickHouse).
2. Спроектировать гибридное представление, сочетающее колоночное хранение плотных полей и компактное хранение разреженных полей, с автоматической миграцией полей между режимами при росте их плотности.
3. Реализовать предложенное представление в кодовой базе Otterbrix, встраиваясь в существующие механизмы SQL-парсера, диспетчера запросов и подсистемы хранения, без существенных изменений низкоуровневых компонентов.
4. Обеспечить корректное поведение системы при параллельных операциях INSERT и SELECT над таблицами с вычисляемой схемой.
5. Выполнить оптимизацию физических операторов (проекция колонок, типизированные предикаты фильтрации, векторизация) для достижения производительности, сопоставимой с существующими промышленными решениями.
6. Провести сравнительное тестирование на стандартном бенчмарке JSONBench с ClickHouse и PostgreSQL в качестве референсных систем.

## 1.5. Научная новизна и практическая значимость

Основная новизна работы заключается в предложении механизма **гетерогенного хранения колонок**: в рамках одной логической таблицы часть колонок хранится в основной таблице (колоночное хранение), часть — в отдельных вспомогательных таблицах формата (_id, value) (разреженное хранение), с автоматической миграцией полей между режимами по мере накопления данных. В отличие от подхода ClickHouse, где редкие поля попадают во внутренний «shared data» формат с ограниченной функциональностью, предложенное решение сохраняет для разреженных колонок полный набор операций (произвольные предикаты, индексы, агрегации) за счёт реализации чтения через LEFT JOIN на уровне исполнителя.

Практическая значимость состоит в получении системы, которая:

- Обходит известные ограничения наивного колоночного хранения JSON (неограниченный рост схемы, раздувание нулевыми значениями).
- Не требует поддержки отдельной подсистемы для документов, что существенно сокращает объём кодовой базы и вероятность ошибок.
- Демонстрирует производительность, сопоставимую с ClickHouse и существенно превосходящую PostgreSQL с JSONB, на стандартном бенчмарке.
- Реализована на основе существующих в Otterbrix механизмов колоночного хранения, что позволяет переиспользовать все накопленные оптимизации (векторизация, zone maps, projection pushdown) без дополнительных усилий.

Изложению исследовательской части, проектированию решения, его реализации, оптимизации и оценке качества посвящены последующие главы настоящей работы.
